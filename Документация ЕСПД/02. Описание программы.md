# Аннотация

Документ содержит описание программы **«Протоколы сборки лаборатории ХИТ»** (далее — **Решение**; техническое обозначение в исходном коде и БД — **BADB**, *Battery Assembly Database*) и составлен в соответствии с требованиями ГОСТ 19.402-78.

По назначению система относится к классу лабораторных информационных систем (ЛИС/ЛИУС; англ. LIMS), но рабочее наименование разрабатываемого решения: **«Протоколы сборки лаборатории ХИТ»**. Техническое обозначение в коде и БД: **BADB** (*Battery Assembly Database*).

Документ описывает общее назначение программы, её логическую структуру, используемые технические средства, порядок вызова и загрузки, структуру входных и выходных данных.

Требования к программе установлены в документе «Техническое задание BADB.00001-01» (далее — **ТЗ**).

# 2. Функциональное назначение

## 2.1. Общее назначение

Программа предназначена для:

1. **Учёта** материалов, полуфабрикатов и готовых изделий в рамках R&D-цикла разработки химических источников тока (электродные материалы, электролиты, сепараторы, ячейки, батарейные модули).
2. **Хранения** параметров процессов, фактических значений, результатов измерений и испытаний в единой реляционной базе данных.
3. **Обработки** данных — автоматизированный расчёт производных величин (масса покрытия, масса активного материала, ёмкость электродов и батарей, N/P-отношение, энергетическая эффективность циклирования).
4. **Трассировки** — обеспечение сквозной связи «партия поставщика → партия ленты → партия электродов → собранная батарея → результаты испытаний».
5. **Анализа** — визуализация данных в виде таблиц, диаграмм, графиков циклирования; построение сводных отчётов.
6. **Контроля доступа** — разграничение прав на уровне проектов и отделов.
7. **Аудита** — фиксация всех изменений данных и действий пользователей.
8. **Экспорта** — формирование печатных отчётов, выгрузка данных в форматы CSV, XLSX, JSON.

## 2.2. Целевая аудитория

Программа предназначена для:

- **Лабораторных операторов** — ввод данных о проведённых операциях, фиксация измерений.
- **Научных сотрудников** — анализ результатов, сравнение серий экспериментов, подготовка отчётов.
- **Руководителей лабораторий** — контроль работ, управление доступом к проектам, формирование сводной отчётности.
- **Системных администраторов** — эксплуатация и сопровождение программы.

## 2.3. Классы решаемых задач

| Класс задач | Примеры |
|---|---|
| Управление справочными данными (reference data management) | Ведение справочников материалов, рецептур, электролитов, сепараторов, оборудования |
| Управление рабочими процессами (workflow management) | Пошаговое оформление процесса изготовления ленты; партии нарезки электродов; сборка батарей |
| Управление качеством (quality management) | Оценка партий поставки материалов; отметка брака электродов; контроль качества собранных батарей |
| Научные расчёты | Ёмкость электродов и батарей (теоретическая и фактическая); поверхностная ёмкость; N/P |
| Обработка измерительных данных | Парсинг протоколов циклирующего оборудования; агрегация по циклам; построение графиков |
| Управление документами | Прикрепление сертификатов качества и PDF-отчётов к объектам базы данных |
| Контроль доступа и аудит | Разграничение прав, журналирование действий, отслеживание изменений |
| Отчётность | Формирование печатных отчётов по лентам, партиям электродов, батареям |

## 2.4. Ограничения области применения

Программа **не предназначена** для:

- Управления технологическим оборудованием в реальном времени (не является SCADA-системой).
- Проведения расчётов конечно-элементным методом, моделирования физико-химических процессов.
- Бухгалтерского и складского учёта (отсутствует система учёта количеств на складе, расходных норм, финансовых документов).
- Работы через публичный Интернет (программа предназначена только для локальной сети).
- Работы на мобильных устройствах в полноэкранном режиме *(отдельная оптимизация под мобильные устройства не выполнялась; базовая работоспособность на планшетах не гарантируется)*.

# 3. Описание логической структуры

```

   │         Клиентская часть                 │
   │  ┌────────────────┐  ┌───────────────┐  │
   │  │ Vanilla v1     │  │ Vue frontend  │  │
   │  │ public HTML/JS │  │ parity/handoff│  │
   │  │ (текущий UI)   │  │ surface       │  │
   │  └───────┬────────┘  └───────┬───────┘  │
   └──────────┼───────────────────┼──────────┘
              │       /api        │
              ▼                   ▼
   ┌──────────────────────────────────────────┐
   │         Серверная часть (Express)        │
   │  ┌──────────────┐  ┌─────────────────┐  │
   │  │  Middleware  │  │  Маршруты API   │  │
   │  │  (auth,      │  │  (19 доменов)   │  │
   │  │   валидация, │  │                 │  │
   │  │   аудит)     │  │                 │  │
   │  └──────────────┘  └────────┬────────┘  │
   └─────────────────────────────┼────────────┘
                                 │
                  ┌──────────────┼──────────────┐
                  ▼              ▼              ▼
           ┌───────────┐  ┌──────────┐  ┌──────────────┐
           │PostgreSQL │  │ Файловое │  │ Python-скрипт │
           │   БД      │  │ хранилище│  │ (парсинг     │
           │   (65     │  │          │  │  циклирования│
           │  таблицы) │  │          │  │   данных)    │
           └───────────┘  └──────────┘  └──────────────┘
```

### 3.1.1. Разделение ответственности

| Уровень | Ответственность |
|---|---|
| Клиентская часть | Отображение данных, пользовательский ввод, page-local валидация и состояние; текущая операторская поверхность — vanilla v1 в `public/` |
| Серверная часть | Бизнес-логика, валидация по контрактам, разграничение доступа, аудит, научные расчёты, взаимодействие с БД |
| СУБД | Хранение данных, поддержание целостности, транзакции, триггеры аудита |

### 3.1.2. Каналы взаимодействия

- Клиент ↔ Сервер: HTTP (HTTPS в production) + JSON.
- Сервер ↔ СУБД: прямое соединение (pool `pg`).
- Сервер ↔ Python-скрипт: через порождение дочернего процесса; обмен через файловую систему.

## 3.2. Серверная часть

### 3.2.1. Точки входа

### 3.2.3. Middleware

Промежуточные обработчики применяются к запросам в следующем порядке (по факту регистрации в `app.js`):

```
1. helmet              → HTTP-заголовки безопасности (глобально)
2. express.json        → Парсинг JSON, лимит тела 10 МБ
3. express.static      → Раздача статических файлов из `public/`
4. express.static      → Раздача загруженных файлов из `uploads/`
5. ipAllowlist         → Фильтрация по CIDR (только на /api/*)
6. rateLimit           → 300 запросов/мин на IP (только на /api/*)
7. Cache-Control: no-store → Запрет кеширования API-ответов
8. registerRoutes      → Регистрация всех маршрутов (см. 3.2.2)
9. errorHandler        → Централизованная обработка ошибок (последний)
```

Внутри маршрутов дополнительно применяются (в порядке вызова):

```
[auth]               → Проверка JWT (для защищённых маршрутов)
[requireRole(...)]   → Проверка роли (admin/lead) для отдельных операций
[validate(schema)]   → Валидация тела запроса по JSON-схеме (AJV)
handler              → Бизнес-логика
trackChanges()       → Вызывается из обработчиков после успешного UPDATE
```

### 3.2.5. Взаимодействие с базой данных

Используется пул соединений `pg.Pool`. Каждое соединение возвращается в пул после обработки запроса. Размер пула настраивается в `config/index.js`.

## 3.8. Ключевые алгоритмы

### 3.8.1. Расчёт плановых количеств компонентов электродной пасты

На странице лент система рассчитывает плановые массы компонентов для
приготовления пасты. Расчёт выполняется в интерфейсе ленты и в печатном отчёте
по ленте; исходные справочные проценты берутся из `tape_recipe_lines`, а выбор
конкретных экземпляров материалов — из `tape_recipe_line_actuals`.

Основные входные данные:

- `tapes.calc_mode`;
- `tapes.target_mass_g`;
- строка активного материала (`cathode_active` или `anode_active`);
- `slurry_percent` строк рецептуры, участвующих в процентном расчёте;
- выбранный `material_instance_id` по каждой строке;
- компонентный состав экземпляра материала, если экземпляр является смесью.

Для режима `from_active_mass` целевая масса активного материала принимается
равной `target_mass_g`:

```
общая_сухая_масса = целевая_масса_активного / (процент_активного / 100)
масса_строки      = общая_сухая_масса × (процент_строки / 100)
```

Для режима `from_slurry_mass` система сначала получает целевую массу активного
материала из входной массы и суммы включённых процентных строк, затем применяет
тот же расчёт строк.

Если выбранный экземпляр материала является смесью, система раскрывает его
компонентные доли:

```
масса_экземпляра_к_взвешиванию =
    оставшаяся_целевая_масса_материала / доля_материала_в_экземпляре
```

Компонентный вклад выбранного экземпляра вычитается из оставшихся целей других
строк рецептуры. Это позволяет корректно учитывать предварительно смешанные
экземпляры и не считать один и тот же компонент дважды.

Строки, не участвующие в процентном расчёте, включая текущую роль
растворителя, сохраняются как фактические значения, но не получают
автоматическую плановую сухую массу.

### 3.8.2. Расчёт ёмкости электродов и батарей

Расчёт производится «по требованию» (on-demand) в маршрутах `/api/electrodes` и `/api/batteries` при выдаче данных клиенту. Производные значения не сохраняются в БД.

**Для одного электрода:**

```
масса_покрытия_г          = масса_электрода_г − средняя_масса_фольги_г
масса_активного_г         = масса_покрытия_г × доля_активного
ёмкость_мА·ч              = масса_активного_г × удельная_ёмкость_мА·ч/г
```

Расчёт выполняется в двух режимах:

| Режим | Источник доли активного |
|---|---|
| Теоретический | `tape_recipe_lines.slurry_percent` для строки с ролью `cathode_active` или `anode_active` |
| Фактический | `tape_recipe_line_actuals` — масса активного / сумма масс сухих компонентов |

**Для партии электродов:**

```
средняя_ёмкость_мА·ч       = среднее по не бракованным электродам
поверхностная_ёмкость_мА·ч/см² = средняя_ёмкость / площадь_электрода_см²
ёмкость_на_сторону         = поверхностная_ёмкость / количество_сторон
```

Количество сторон: 1 для одностороннего нанесения, 2 для двустороннего (получается из `tape_step_coating.coating_sidedness` ленты-источника).

**Для батареи:**

```
Σ_катодов              = сумма ёмкостей выбранных катодных электродов
Σ_анодов               = сумма ёмкостей выбранных анодных электродов
лимитирующая_ёмкость   = min(Σ_катодов, Σ_анодов)
N/P                    = Σ_анодов / Σ_катодов
```

Для полуячейки (`form_factor='coin'` + `coin_cell_mode='half_cell'`) лимитирующая ёмкость и N/P не применяются; отображается только ёмкость рабочего электрода.

**Обработка отсутствующих данных:** если любой из входов отсутствует (нет плотности, нет удельной ёмкости, нет измерений фольги, электрод бракован), соответствующий производный показатель возвращается как `null` и отображается в интерфейсе как «—». Паника или аварийное завершение алгоритма не допускаются.

### 3.8.3. Пропагация типа нанесения (sidedness)

Тип нанесения — одно из значений `one_sided` / `two_sided` — хранится только в одном месте: `tape_step_coating.coating_sidedness` (стадия 5 процесса изготовления ленты).

На уровне электрода значение **вычисляется при загрузке**: `electrode.sidedness = tape.sidedness`; в БД не хранится, в интерфейсе — только для просмотра.

На уровне батареи: при добавлении электрода в стек сервер проверяет, что его `sidedness` совпадает с `sidedness` первого выбранного электрода. Попытка смешать электроды с разным типом нанесения отклоняется с сообщением: «Нельзя смешивать 1- и 2-сторонние электроды в одной ячейке».

Для Pouch/призматического/цилиндрического стека миграции d031/d036 проверяют каждую вставку. Поэтому сервис сначала валидирует итоговый набор, а затем сохраняет строки trigger-safe парами `A1, C1, A2, C2`, сохраняя исходные `position_index`. Это защищает валидные cathode-first API payloads от ложного отказа DB-триггера.

### 3.8.4. Оптимистичная блокировка

В редактируемых таблицах рабочих процессов присутствует целое поле `version`, увеличиваемое на 1 при каждом `UPDATE`. Поле добавлено миграцией `003_optimistic_locking.sql` на таблицах: `tapes`, `electrodes`, `batteries`, `tape_recipes`, `projects`. Для таблиц-журналов (`raw_submissions`, `auth_log` и т.п.) и чистых справочников поле `version` не используется.

Протокол обновления:

1. Клиент при чтении получает текущее значение `version`.
2. При отправке UPDATE клиент передаёт это значение в теле запроса.
3. Сервер выполняет запрос: `UPDATE ... WHERE id = $id AND version = $expected`.
4. Если количество затронутых строк равно 0 — возвращается HTTP 409 Conflict.
5. Клиент предлагает пользователю перезагрузить данные и повторить попытку.

Этот механизм устраняет конкурентные перезаписи без необходимости явных блокировок на уровне СУБД.

### 3.8.5. Защита от перебора паролей

Защита реализована в `routes/auth.js` для маршрутов `POST /login` и `POST /change-password-public`. Алгоритм при каждой попытке входа:

1. Открывается транзакция; берётся advisory-блокировка PostgreSQL `pg_advisory_xact_lock(hashtext(lower(login)))`. Блокировка действует до конца транзакции и исключает гонку условий при одновременных параллельных попытках под одним логином (закрывает race «прочитать счётчик → не превышено → вставить запись о неудаче», который мог пропустить N параллельных попыток мимо лимита).
2. Подсчитывается число неудачных попыток за скользящее окно: `SELECT COUNT(*) FROM auth_log WHERE login = $1 AND event = 'login_failed' AND created_at > now() - make_interval(mins => $2)` (окно — `config.rateLimit.lockoutWindowMinutes`, по умолчанию 60 минут).
3. Если число неудач ≥ `config.rateLimit.maxFailedAttempts` (по умолчанию 10) — попытка отклоняется с HTTP 429 `Too Many Failed Attempts` и заголовком `retryAfter` (в секундах); в `auth_log` записывается событие `login_failed` с пометкой `reason: 'locked_out'`. Проверка пароля не выполняется.
4. Иначе ищется пользователь по логину (с регистронезависимым сравнением). Если пользователь не найден — `auth_log: login_failed (reason: user_not_found)`, ответ 401.
5. Если у пользователя `active = false` — `auth_log: login_failed (reason: account_disabled)`, ответ 403 «Учётная запись отключена».
6. Если хеш пароля не совпадает — `auth_log: login_failed (reason: wrong_password)`, ответ 401.
7. При успешном входе — `auth_log: login_success`, выпуск JWT-токена, ответ 200 со списком проектов пользователя.

Все попытки (успешные и неуспешные) записываются в `auth_log` с указанием IP-адреса (`req.ip`), User-Agent, и причины (для неудач). Скользящее окно автоматически «прощает» старые попытки — отдельный процесс сброса счётчика не нужен.

**Сброс пароля забывшему пользователю** реализован отдельным маршрутом `POST /api/auth/admin-reset-password/:userId` (только для роли admin). Алгоритм: проверка существования целевой записи; хеширование нового пароля через `bcrypt`; обновление `users.password_hash` и инкремент `users.token_version` (что инвалидирует все ранее выданные токены пользователя); запись события `password_reset_by_admin` в `auth_log` с указанием инициатора (admin) в поле `details`. После сброса целевой пользователь должен войти с временным паролем и сразу сменить его через `POST /change-password-public`.

### 3.8.6. Цепочка аудита

Трёхуровневая цепочка, все уровни являются append-only таблицами:

| Уровень | Таблица | Гранулярность | Триггер |
|---|---|---|---|
| Аутентификация | `auth_log` | Каждая попытка входа/выхода | Серверный код в `routes/auth.js` |
| Активность | `activity_log` | Каждая CRUD-операция | Middleware `trackChanges` + ручные вызовы |
| Изменение полей | `field_changelog` | Каждое изменённое поле при UPDATE | Middleware `trackChanges` после успешного UPDATE |

При UPDATE middleware `trackChanges` сравнивает состояние записи до и после операции и записывает все отличающиеся поля с парой значений «старое/новое».

### 3.8.7. Парсинг протоколов циклирования

Последовательность:

1. Клиент загружает файл протокола; серверный маршрут `/api/cycling` сохраняет его в `uploads/cycling/raw/`.
2. Создаётся запись в `cycling_sessions` со статусом `parsing`.
3. Порождается дочерний процесс Python: `python3 scripts/parse_cycling.py <input_file> <output_spec>`.
4. Скрипт парсит файл, записывает точки данных в таблицу `cycling_datapoints`, рассчитывает агрегаты по циклам и записывает их в `cycling_cycle_summary`.
5. После завершения скрипта сервер обновляет статус сеанса на `completed` или `failed`.

## 5.1. Установка

Подробная инструкция по развёртыванию — в «Руководстве системного программиста» (ГОСТ 19.503-79). Ниже — краткое описание процесса.

Последовательность первоначальной установки:

1. Клонирование репозитория:
   ```bash
   git clone <URL> BADB_main
   cd BADB_main
   ```
2. Установка зависимостей серверной части:
   ```bash
   npm install
   ```
3. Установка зависимостей Vue frontend требуется только для режима `npm run dev` / parity-работ:
   ```bash
   cd client-web && npm install
   ```
4. Создание базы данных PostgreSQL и применение миграций (см. «Руководство системного программиста»). Для Windows/encoding-sensitive среды использовать также `migrations_ASCII/` как mirror.
5. Настройка переменных окружения. Переменные задаются стандартными средствами операционной системы (в Windows — через свойства системы или PowerShell `$env:`; в Linux — через `export` или systemd unit). Опционально может использоваться файл `.env` (Node 20+ читает его флагом `--env-file=.env` нативно, без дополнительных пакетов). Применяемые переменные:
   - `PORT=3003` — порт HTTP-сервера (по умолчанию 3003);
   - `BIND_HOST` — интерфейс прослушивания: `0.0.0.0` (по умолчанию, все интерфейсы) / `127.0.0.1` (только loopback) / конкретный LAN-IP. Рекомендация для продуктивного развёртывания — указать LAN-IP лаборатории явно, чтобы избежать прослушивания на интерфейсах, выходящих за пределы локальной сети;
   - `DB_NAME`, `DB_USER` — параметры подключения к PostgreSQL, читаемые `config/index.js`; host/port/password передаются стандартными libpq-переменными `PGHOST`, `PGPORT`, `PGPASSWORD`;
   - `JWT_SECRET` — секрет подписи JWT-токенов (обязательно для production; в коде есть проверка на старте, отказывающая запуск с дефолтным значением);
   - `ALLOWED_IPS` — опциональный список разрешённых CIDR-диапазонов для `/api/*` (см. описание `middleware/ipAllowlist.js` в §3.2.3). Пустая или не заданная переменная — фильтр отключён (обратная совместимость);
   - `VUE_HTML_REDIRECTS=true` — опциональное включение redirects vanilla HTML routes на Vue routes; по умолчанию текущие vanilla pages доступны напрямую;
   - `AUTH_BYPASS=true` + `BYPASS_LOGIN=<логин>` — режим автоматического входа для отладки (только разработка, в production запрещён).

# 6. Входные данные

## 6.1. Источники входных данных

| Источник | Канал | Основной формат |
|---|---|---|
| Пользователь (vanilla v1 веб-интерфейс) | `public/` pages → `/api/*` | JSON; Base64 для отдельных вложений; multipart для raw-файлов циклирования |
| Внешние submitter-клиенты, включая возможное будущее восстановление Excel/VBA | `/api/submit` | JSON по JSON-схемам |
| Файлы протоколов циклирования | Загрузка через веб-интерфейс | `.csv`, `.xlsx`, `.xls`, `.txt`, обрабатываются Python-парсером |
| PDF-отчёты электрохимических испытаний | Загрузка через веб-интерфейс | PDF (до 6 МБ) |
| Паспорта качества и сертификаты материалов | Загрузка через веб-интерфейс | PDF / изображения |
| SQL-миграции и резервные копии | Применяются системным администратором | SQL-файлы |

## 6.2. Структура данных JSON-запросов

Тела POST/PATCH запросов подчиняются JSON-схемам. Пример минимального запроса создания ленты:

```json
{
  "project_id": 15,
  "tape_recipe_id": 42,
  "name": "Лента LFP 2026-04-22 A",
  "notes": "Пробная партия",
  "calc_mode": "solids",
  "target_mass_g": 5.0
}
```

*Примечания к примеру:* поле `created_by` **не передаётся клиентом** — сервер принудительно устанавливает его в идентификатор аутентифицированного пользователя (`req.user.userId`). Попытка передать другое значение игнорируется.

Полная структура — в контрактах `contracts/schemas/*.v1.json`. См. также Приложение Г.

## 6.3. Валидация входных данных

Валидация выполняется на двух уровнях:

1. **Клиентская валидация** — в текущих vanilla-формах и page-specific JavaScript: обязательность полей, форматы, диапазоны. Цель — ранняя обратная связь пользователю.
2. **Серверная валидация** — обязательная проверка по JSON-схемам в middleware `validate`. При несоответствии — HTTP 400 с перечислением нарушений.

Дополнительная бизнес-валидация выполняется в обработчиках маршрутов (например, проверка ограничений на форм-фактор батареи при выборе электродов).

## 6.4. Ограничения на входные данные

| Ограничение | Значение |
|---|---|
| Максимальный размер JSON-запроса | 10 МБ |
| Максимальный размер файла (Base64) | 6 МБ |
| Максимальный размер raw-файла циклирования (multipart) | 100 МБ |
| Максимальная длина строкового поля | 255 символов (если не указано иное в схеме) |
| Максимальная длина текстового поля без ограничения | неограничена (тип `TEXT`) |
| Разрешённые MIME-типы для PDF | `application/pdf` |
| Разрешённые MIME-типы для изображений | `image/png`, `image/jpeg`, `image/webp` |

## Приложение Г. Пример валидации по JSON-схеме

Контракт `tape_prepare.v1.json` определяет формат пакетной отправки данных о подготовке ленты от внешнего submitter-клиента через `/api/submit`. Фрагмент схемы:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "$id": "tape_prepare.v1",
  "title": "Tape Preparation Submission",
  "type": "object",
  "required": [
    "contract_version", "submission_type", "submission_id",
    "created_at", "user", "machine", "checksum", "payload"
  ],
  "properties": {
    "contract_version": { "const": "tape_prepare.v1" },
    "submission_type":  { "const": "tape_prepare" },
    "submission_id":    { "type": "string", "format": "uuid" },
    "created_at":       { "type": "string", "format": "date-time" },
    "user":             { "type": "string", "minLength": 1,
                          "description": "Логин оператора" },
    "machine":          { "type": "string",
                          "description": "Имя хоста submitter-клиента" },
    "checksum":         { "type": "string",
                          "pattern": "^[a-f0-9]{64}$",
                          "description": "SHA-256 хеш payload" },
    "payload": {
      "type": "object",
      "required": ["project_id", "tape_recipe_id",
                   "tape_name", "actuals", "steps"],
      "properties": {
        "project_id":     { "type": "integer", "minimum": 1 },
        "tape_recipe_id": { "type": "integer", "minimum": 1 },
        "tape_name":      { "type": "string", "minLength": 1 },
        "actuals":        { "type": "array", "items": { ... } },
        "steps":          { "type": "array", "items": { ... } }
      }
    }
  }
}
```

Ключевые особенности:

- Пакет содержит **метаданные отправки** (`submission_id`, `created_at`, `user`, `machine`, `checksum`) — для регистрации в `raw_submissions` с проверкой целостности.
- Полезная нагрузка (`payload`) содержит `project_id`, `tape_recipe_id`, имя ленты, массив фактических значений рецепта (`actuals`) и массив стадий (`steps`) — чтобы одна отправка отражала всю ленту целиком.
- При несоответствии схеме сервер возвращает HTTP 400 с массивом нарушений.
- Альтернативный путь для веб-интерфейса vanilla/Vue — отдельные POST-запросы к `/api/tapes`, `/api/tapes/:id/actuals`, `/api/tapes/:id/steps` без требования контрактного пакета.
