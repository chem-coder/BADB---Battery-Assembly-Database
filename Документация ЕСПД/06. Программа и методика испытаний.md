# 1. Объект испытаний

## 1.1. Наименование

Программное обеспечение лабораторной информационно-управляющей системы «Химические источники тока» (ЛИМС-ХИТ; техническое обозначение в исходном коде — BADB), версия 1.0.

## 1.2. Обозначение

BADB.00001-01 *(обозначение — @уточнить)*.

## 1.3. Состав объекта испытаний

Объект испытаний включает:

- Серверную часть (Node.js + Express), запускаемую из `server.js`;
- Клиентскую часть vanilla v1 (`public/`) — текущие рабочие и справочные страницы, page-specific JavaScript и печатные отчёты;
- Vue 3 клиент (`client-web/`) — отдельную frontend synchronization/handoff поверхность, не источник текущего vanilla v1 поведения;
- Python-парсер протоколов циклирования (`scripts/parse_cycling.py`);
- База данных PostgreSQL 16 со структурой, определяемой миграциями из каталога `migrations/`;
- Комплект JSON-схем валидации (`contracts/schemas/`).

Объект испытаний **не включает** интеграцию с Excel-надстройкой `DatabaseUI.xlam` (проверяется отдельными испытаниями).

# 2. Цель испытаний

## 2.1. Основные цели

Испытания проводятся с целью установить:

1. **Соответствие функциональных возможностей программы требованиям ТЗ** (раздел 4.1 ТЗ).
2. **Соответствие программы требованиям к надёжности** (раздел 4.2 ТЗ).
3. **Соответствие программы требованиям к безопасности** (раздел 4.8.1 ТЗ).
4. **Соответствие программы требованиям к производительности** (раздел 4.8.2 ТЗ).

## 2.2. Частные цели

- Выявить все замечания и недочёты, существенно затрудняющие работу пользователей.
- Выявить расхождения между фактической реализацией и требованиями ТЗ.
- Получить объективные данные для принятия решения о готовности программы к промышленной эксплуатации.

# 3. Требования к программе

Подробный перечень требований — в разделе 4 **ТЗ BADB.00001-01**. В настоящем документе приводится агрегированный список требований, подлежащих проверке.

## 3.1. Функциональные требования

Программа должна обеспечивать выполнение всех функций, описанных в разделе 4.1 ТЗ. Конкретные функции проверяются в тест-кейсах раздела 6 настоящего документа.

## 3.2. Требования к надёжности

- Сохранность данных в append-only журналах (`auth_log`, `activity_log`, `field_changelog`, `raw_submissions`).
- Корректная обработка конфликтов оптимистичной блокировки (возврат HTTP 409).
- Корректная обработка ошибок валидации (возврат HTTP 400 с подробностями).
- Устойчивость к сетевым сбоям (восстановление соединения без потери данных).
- Возможность восстановления из резервной копии.

## 3.3. Требования к безопасности

- Ролевая модель (`admin` / `lead` / `employee`).
- Защита от перебора паролей (блокировка после 10 попыток).
- Ограничение частоты запросов (300/мин на IP).
- Корректная работа IP-allowlist.
- Инвалидация токенов при смене пароля.
- Запрет `AUTH_BYPASS` в продуктивной среде.
- Обязательность `JWT_SECRET` в продуктивной среде.

## 3.4. Требования к производительности

| Характеристика | Нормативное значение |
|---|---|
| Время отклика на простой GET-запрос (чтение одной записи) | ≤ 200 мс |
| Время отклика на GET-запрос списка до 1000 записей | ≤ 500 мс |
| Время отклика на сложный аналитический запрос (сводка ёмкости партии) | ≤ 1000 мс |
| Количество одновременных активных пользователей | ≥ 50 без деградации |
| Обработка загрузки файла 6 МБ | ≤ 5 с |
| Парсинг протокола циклирования размером 10 МБ | ≤ 60 с |

# 5. Средства и порядок испытаний

## 5.1. Виды испытаний

Испытания состоят из трёх этапов:

### 5.1.1. Этап 1 — Предварительная проверка (внутренние испытания)

**Цель:** убедиться, что программа функционирует в предусмотренных сценариях без критических отказов.

**Состав проверок:** разделы 6.1–6.16 настоящей методики.

**Исполнитель:** разработчики (Меняйлов Д.С., Мараулайте Д.К.).

**Условия:** тестовая установка на отдельной базе данных.

**Длительность:** 2–3 рабочих дня.

**Результат:** внутренний протокол, перечень выявленных замечаний.

### 5.1.2. Этап 2 — Опытная эксплуатация

**Цель:** проверить работоспособность программы в условиях, приближенных к штатным, на реальных данных.

**Состав проверок:** функциональное использование во всех лабораторных сценариях.

**Исполнители:** лабораторный персонал ООО «РЭНЕРА» (@уточнить список сотрудников).

**Условия:** установка на продуктивный сервер, реальная работа с данными лаборатории.

**Длительность:** не менее 30 календарных дней *(@уточнить с руководителем направления)*.

**Результат:** протокол опытной эксплуатации, перечень замечаний, сведения о нагрузке, предложения по улучшению.

### 5.1.3. Этап 3 — Приёмо-сдаточные испытания

**Цель:** формально установить соответствие программы требованиям ТЗ.

**Состав проверок:** демонстрация устранения замечаний этапа 2; повторное прохождение ключевых тест-кейсов настоящей методики (разделы 6.1–6.12).

**Исполнители:** приёмная комиссия (@уточнить состав), разработчики.

**Условия:** продуктивная установка.

**Длительность:** 1–2 рабочих дня.

**Результат:** **Акт по результатам опытной эксплуатации** (составляется руководителем разработки Д.К. Мараулайте) и (при положительном исходе) заключение о готовности к промышленной эксплуатации.

## 5.2. Необходимые технические средства

### 5.2.1. Для этапа 1 (предварительная проверка)

- Компьютер разработчика с установленным ПО (macOS/Linux, Node.js 22, PostgreSQL 16, Python 3.11+, git);
- Отдельная тестовая БД;
- Предзаполненные справочные данные (тестовые материалы, рецепты, пользователи);
- Браузер последней версии для проверки клиентской части;
- Доступ к файлам протоколов циклирования (реальные или синтетические).

### 5.2.2. Для этапа 2 (опытная эксплуатация)

- Продуктивный сервер с развёрнутой программой (см. «Руководство системного программиста»);
- Рабочие места лабораторных сотрудников;
- Реальные лабораторные данные для ввода в систему;
- Автоматическое резервное копирование (ежедневно);
- Система сбора обратной связи от пользователей (форма «Обратная связь» в самой программе + канал прямой связи с разработчиком).

### 5.2.3. Для этапа 3 (приёмо-сдаточные испытания)

- Доступ к продуктивному серверу;
- Выгрузка журналов, собранных в ходе опытной эксплуатации;
- Сводный отчёт по выявленным замечаниям и мерам их устранения.

## 5.3. Порядок проведения испытаний

1. Подготовить стенд испытаний в соответствии с 5.2.
2. Выполнить тест-кейсы раздела 6 настоящей методики в приведённом порядке.
3. Для каждого тест-кейса зафиксировать:
   - Дату и время выполнения;
   - Исполнителя;
   - Результат (пройден / не пройден);
   - Описание замечаний (при наличии).
4. Сформировать протокол испытаний.
5. По завершении — составить акт, отражающий результаты.

## 5.4. Критерии приёмки

Программа считается прошедшей испытания, если:

1. **Все критические функции выполняются без ошибок.** «Критические функции» — те, без которых невозможно базовое использование: вход, CRUD справочников, создание ленты, создание электродов, сборка батареи, загрузка данных циклирования.
2. **Все специальные требования безопасности соблюдаются.** Проверки раздела 6.10 должны быть пройдены на 100 %.
3. **Замечания, не являющиеся критическими, зафиксированы и согласованы** с заказчиком: либо устранены до приёмки, либо перенесены в план последующих обновлений.
4. **Программная документация соответствует реализации** и утверждена заказчиком.
5. **Успешно выполнен откат с резервной копии** (проверяется в разделе 6.12).
6. **Vanilla v1 release-candidate checks выполнены:** `git diff --check`, `npm test`, `npm run contract:vanilla`, `npm run smoke:vanilla`.
7. **Windows/lab БД готова к пилоту:** authoritative ledger `public.schema_migrations` создан `d032_create_schema_migrations_table.sql` и показывает `dima=21`, `dalia=22` после `d034`; `d031_harden_battery_stack_validate_trigger.sql` применён и проверен прямым SQL-запросом; ожидаемые значения `allows_extra_anode=true`, `allows_extra_cathode=false`, `handles_update=true`.
8. **Destructive-action safety проверена вручную:** для батарей выполнен guided delete spot-check с hard blocker, вариантом возврата электродов, вариантом списания электродов и проверкой записи в `activity_log`.

# 6. Методы испытаний

## 6.1. Группа: Аутентификация и управление доступом

### 6.1.1. ТК-AUTH-01. Успешный вход в систему

**Предусловие:** в БД существует пользователь с логином `test_user` и известным паролем.

**Шаги:**

1. Открыть страницу входа.
2. Ввести логин и корректный пароль.
3. Нажать «Войти».

**Ожидаемый результат:**

- Отображается главный экран.
- В `auth_log` появляется запись со значением `event = 'login_success'`, полями `user_id`, `login`, `ip_address`, `user_agent`, `created_at`.

**Критерий:** запись в БД создана, время отклика ≤ 2 с.

### 6.1.2. ТК-AUTH-02. Неуспешный вход с неверным паролем

**Шаги:**

1. Открыть страницу входа.
2. Ввести логин `test_user` и неверный пароль.
3. Нажать «Войти».

**Ожидаемый результат:**

- Отображается сообщение «Неверный логин или пароль».
- В `auth_log` — запись с `event = 'login_failed'`.
- Счётчик неуспешных попыток увеличивается.

### 6.1.3. ТК-AUTH-03. Автоматическая блокировка после превышения попыток

**Шаги:**

1. Выполнить 10 раз ТК-AUTH-02 с одним и тем же логином в пределах окна `lockoutWindowMinutes` (по умолчанию 60 минут).
2. На 11-й попытке ввести **правильный** пароль.

**Ожидаемый результат:**

- На 11-й попытке — HTTP 429 `Too Many Failed Attempts` с заголовком `retryAfter` (число секунд до сброса окна), без проверки пароля.
- В таблице `auth_log` — 11 записей с `event = 'login_failed'`; в 11-й записи поле `details` содержит `{"reason": "locked_out"}`.
- Блокировка автоматически снимается, как только все неудачные попытки выходят за пределы скользящего окна — то есть через `lockoutWindowMinutes` минут после первой попытки. Отдельной операции «разблокировки» не требуется.

### 6.1.4. ТК-AUTH-04. Проверка истечения токена

**Шаги:**

1. Войти в систему.
2. Дождаться истечения 8 часов (либо эмулировать просрочку): сгенерировать токен с просроченным `exp` при помощи `jsonwebtoken` и подменить значение в `localStorage` по ключу `badb_auth_token`.
3. Попытаться выполнить любое действие, требующее авторизации (например, обновить страницу `/tapes`).

**Ожидаемый результат:**

- Сервер возвращает HTTP 401 на любой API-запрос.
- Клиент обрабатывает 401 через `axios`-интерсептор: сбрасывает состояние `useAuthStore` и перенаправляет на страницу входа.
- Сообщение «Сессия истекла. Требуется повторный вход».

### 6.1.5. ТК-AUTH-05. Инвалидация токена при смене пароля

**Шаги:**

1. Войти в систему в браузере A.
2. В том же аккаунте из браузера B сменить пароль.
3. В браузере A попытаться выполнить любое действие.

**Ожидаемый результат:** перенаправление на страницу входа (токен инвалидирован).

### 6.1.6. ТК-AUTH-06. Ролевой доступ: `employee` не видит администрирование

**Шаги:**

1. Войти под пользователем с ролью `employee`.

**Ожидаемый результат:** в боковом меню отсутствуют разделы «Пользователи», «Доступ», «Активность», «Аудит».

### 6.1.7. ТК-AUTH-07. Ролевой доступ: `employee` получает 403 при прямом обращении

**Шаги:**

1. Войти под `employee`.
2. Вручную в браузере открыть URL `/access`.

**Ожидаемый результат:** перенаправление на главную с параметром `?denied=lead`; на главной отображается уведомление об отказе.

### 6.1.8. ТК-AUTH-08. Доступ к проекту с истёкшим сроком

**Предусловие:** пользователю `test_user` предоставлен доступ к проекту X с `expires_at` в прошлом.

**Шаги:**

1. Войти под `test_user`.
2. Попытаться открыть данные проекта X.

**Ожидаемый результат:** данные не отображаются; в списке проекта X нет.

### 6.1.9. ТК-AUTH-09. Выход из системы

**Шаги:**

1. Войти в систему.
2. В меню пользователя выбрать «Выход».

**Ожидаемый результат:**

**Шаги:**

1. От имени `admin_user` отправить запрос:
   ```
   POST /api/auth/admin-reset-password/<id_forgetful_user>
   Authorization: Bearer <jwt_admin>
   Body: {"new_password":"<временный_пароль>"}
   ```
2. Передать `forgetful_user` временный пароль.
3. `forgetful_user` выполняет вход с временным паролем и переходит к форме смены пароля.
4. `forgetful_user` задаёт новый постоянный пароль через `POST /api/auth/change-password-public`.

**Ожидаемый результат:**

- Шаг 1 — HTTP 200; в `auth_log` событие `password_reset_by_admin` с `details.reset_by_user_id = <admin_id>`.

- Шаг 4 — пароль обновлён, выпущен новый JWT, прежний временный больше не действует.

**Негативная проверка:** запрос на шаге 1 от пользователя без роли `admin` отклоняется с HTTP 403.

**Шаги:**

- Поверхностная ёмкость (теор.): `6.68 / 1.767 ≈ 3.78` мА·ч/см².
- Ёмкость на сторону (теор., 2 стороны): `3.78 / 2 = 1.89` мА·ч/см².

**Ожидаемый результат:** сводка совпадает с расчётом (с точностью до округления).

**Ожидаемый результат:**

- В таблице `tape_projects` присутствуют две записи `(T1, Проект-A)` и `(T1, Проект-B)`.
- В таблице `electrode_cut_batch_projects` для `B1` автоматически появились две записи (унаследованы от `tape_projects` родительской ленты `T1` при создании партии).
- В таблице `battery_projects` запись `(Bat1, Проект-A)`.
- На странице `Проект-A` видны: лента `T1`, партия `B1`, батарея `Bat1`.
- На странице `Проект-B` видны: лента `T1` и партия `B1` (батарея не входит, так как добавлена только в `Проект-A`).
- Поля `tapes.project_id` и `batteries.project_id` сохраняют значение «исходного» проекта (`Проект-A`) для обратной совместимости с существующим UI; у партии нарезки fallback-проект берётся от ленты-источника, а каноническая принадлежность хранится в `electrode_cut_batch_projects`.

## 6.16. Группа: Vanilla v1 operator surface

### 6.16.1. ТК-UI-01. Текущие страницы, фильтры и открытие записей

**Шаги:**

4. Прокрутить открытую запись и проверить закреплённую верхнюю панель.

**Ожидаемый результат:** все текущие страницы открываются; фильтры соответствуют документированному набору; row-open и sticky header работают на страницах, где это предусмотрено; Vue parity-поверхность не используется как источник текущего результата.

### 6.16.2. ТК-UI-02. Destructive-action safety matrix

**Шаги:**

1. Проверить typed confirmation и delete-check для лент (`DELETE TAPE <id>`), рецептур (`DELETE RECIPE <id>`), электролитов (`DELETE ELECTROLYTE <id>`) и сепараторов (`DELETE SEPARATOR <id>`).
2. Проверить guided delete батареи по ТК-BAT-11.
3. Проверить, что проекты и пользователи блокируются backend-ом при зависимостях, а отделы в vanilla v1 не имеют удаления.

**Ожидаемый результат:** разрушительные действия требуют подтверждения или блокируются согласно текущим правилам; связи с используемыми сущностями не повреждаются.
