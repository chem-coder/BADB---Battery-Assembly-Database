## 1. Цели и задачи разрабатываемого решения

**«Протоколы сборки лаборатории ХИТ»** — рабочее наименование разрабатываемого
решения (далее — Решение). Техническое обозначение в исходном коде, БД и
именах файлов — **BADB** (*Battery Assembly Database*).

По назначению система относится к классу лабораторных информационных систем
(ЛИС/ЛИУС; англ. LIMS), но рабочее наименование разрабатываемого решения:
**«Протоколы сборки лаборатории ХИТ»**. Техническое обозначение в коде и БД:
**BADB** (*Battery Assembly Database*).

Решение предназначено для автоматизации учёта, обработки и научного анализа
лабораторных данных полного цикла исследования и разработки химических
источников тока (ХИТ) Центра ХИТ ООО «РЭНЕРА»: электродных материалов,
электролитов, сепараторов, собранных ячеек и батарейных модулей различных
электрохимических систем.

Основные задачи:

- учёт материалов, рецептов, электродных лент, партий электродов, сепараторов,
  электролитов и аккумуляторов;
- связь сырья, технологических операций и итоговых изделий — обеспечение
  сквозной прослеживаемости «материал → рецепт → лента → партия электродов →
  аккумулятор → электрохимические испытания»;
- учёт результатов циклических испытаний: загрузка файлов измерений с
  приборных стендов (ELITECH), парсинг, хранение сессий и сырых datapoints в
  единой БД, интерактивные графики, экспорт в Excel со структурированной
  разбивкой по листам (метаданные сессии, per-cycle сводки, сырые datapoints,
  параметры графиков). Каждая сессия привязана к конкретному собранному
  аккумулятору;
- снижение риска потери лабораторных данных и ошибок ручного учёта;
- формирование печатных отчётов и протоколов по ключевым сущностям.

Текущая production-версия рабочих процессов от материала до сборки
аккумулятора — vanilla v1/v1.1 (release candidate согласно ЕСПД v0.1.16).
Модуль циклических испытаний реализован в составе следующей версии
веб-интерфейса (Vue/V2); параллельно идёт приведение остальных страниц V2 к
поведенческому паритету с vanilla v1 для постепенной замены в будущих
релизах. **На требования к развёртываемой инфраструктуре это не влияет:** оба
интерфейса используют те же серверные компоненты, ту же базу данных, тот же
сервер.

## 2. Архитектура решения в целом

Решение реализовано как классическое внутрисетевое веб-приложение
клиент-серверной архитектуры:

```text
┌────────────────┐  HTTP(S)    ┌─────────────────────┐  TCP   ┌──────────────┐
│   Браузер      │ ──────────► │   Express :3003     │ ─────► │ PostgreSQL   │
│   оператора    │             │   Node.js 22 LTS    │  5432  │ 16.x         │
└────────────────┘             │   - REST API /api/* │        │ badb_app_v1  │
                               │   - vanilla v1 HTML │        └──────────────┘
                               │   - статика uploads │              ▲
                               └─────────────────────┘              │
                                          ▲                         │
                                          │ psql (только админ)     │
                                  ┌───────┴────────┐                │
                                  │  Администратор ├────────────────┘
                                  └────────────────┘
```

Компоненты:

- **PostgreSQL 16.x** — основная реляционная СУБД и источник истины для
  структурированных лабораторных данных;
- **Каталог `uploads/`** — источник истины для файловых вложений (метаданные
  и ссылки хранятся в БД; **корректная резервная копия решения требует
  синхронного бэкапа обоих хранилищ**);
- **Node.js 22 LTS + Express 5** — серверное приложение и REST API под `/api/*`;
- **vanilla v1** — статический веб-интерфейс в каталоге `public/`, обслуживается
  Express; текущая операторская поверхность;
- **Vue/Vite клиент** (`client-web/`) — следующая версия фронтенда в разработке,
  на инфраструктурные требования не влияет;
- **SQL-миграции** (`migrations/` и ASCII-зеркало `migrations_ASCII/`) —
  единственный канонический способ обновления структуры БД; журнал применения —
  в таблице `public.schema_migrations`;
- **Служебные скрипты:** резервное копирование (`scripts/backup.js`), smoke-тесты
  vanilla API, проверка контракта.

Обычные пользователи работают через браузер. Прямой доступ к PostgreSQL — только
у администратора и сопровождающего разработчика для миграций, резервного
копирования, восстановления и точечной диагностики.

## 3. Архитектура фронтенда

**Vanilla v1 — текущая production-поверхность для workflow от материала до
сборки аккумулятора.** Около 10 рабочих страниц в `public/workflow/` (ленты,
электроды, сборка, печатные отчёты) и справочные страницы в
`public/reference/`. Технологии: чистый JavaScript без сборщика и
SPA-фреймворка, fetch API, HTML/CSS без препроцессоров. Поддерживаемые
операции: ввод и редактирование лабораторных сущностей, списки и фильтры,
печатные отчёты, безопасные сценарии удаления с проверкой зависимостей,
расчётные подсказки для рецептов и электродов, авторизованная работа по
ролям.

**Vue/V2** в `client-web/` решает две задачи одновременно:

- содержит модуль циклических испытаний (`CyclingPage.vue`,
  `CyclingCharts.vue`, `CyclingStylePopover.vue`, composable
  `useCyclingStyles.js`) — единственная поверхность, на которой реализована
  работа с данными циклирования; в vanilla v1 этой страницы нет;
- параллельно идёт приведение остальных страниц V2 (материалы, рецепты,
  электроды, аккумуляторы, проекты и пр.) к поведенческому паритету с
  vanilla v1 — для постепенной замены в будущих релизах.

Стек V2: Vue 3 + Vite + PrimeVue + Chart.js + Cytoscape (полный перечень
зависимостей — в `package.json` и в Приложении к «01. Техническому заданию»
§4.5.1).

## 4. Архитектура бэкенда, базы и аналитики

### Бэкенд (Node.js)

- **Среда исполнения:** Node.js 22 LTS;
- **Веб-фреймворк:** Express 5 (модульная компоновка); порядка 20 файлов
  маршрутов в `routes/`, порядка 30 доменных сервисов в `services/`;
- **Драйвер PostgreSQL:** `pg`;
- **Middleware** (порядок в `app.js`): `helmet` → `express.json` → static
  (`public/`, `/uploads`) → опциональный IP-allowlist (CIDR) → rate-limit →
  cache-control → роуты → централизованный обработчик ошибок;
- **Валидация контрактов API:** `ajv` + JSON Schema draft-07
  (`contracts/schemas/`).

Основные доменные группы API: авторизация и пользователи; материалы и их
свойства; рецепты, электролиты, сепараторы; ленты (полный цикл от замеса до
каландрирования); партии электродов; аккумуляторы (сборка); циклические
испытания (см. ниже); проекты и контроль доступа; печатные отчёты; активность и
трассировка. Полный реестр маршрутов (порядка 200 REST-эндпоинтов) — в
Приложении А «Описания программы».

**Реализация модуля циклических испытаний:** REST API под `/api/cycling/*`
(загрузка файлов, сессии, per-cycle summary, datapoints); парсинг файлов
ELITECH через Python-скрипт `scripts/parse_cycling.py` с записью в БД
(сессия + per-cycle сводка + сырые datapoints); исходные файлы сохраняются в
`uploads/cycling/`; экспорт в CSV и XLSX (через `exceljs`) с многолистовой
структурой (метаданные, per-cycle сводки, сырые datapoints, параметры
графиков).

### База данных (PostgreSQL)

- **СУБД:** PostgreSQL 16.x;
- **Схема:** порядка 65 публичных таблиц; справочники и workflow-таблицы
  связаны внешними ключами и сервисной валидацией; отдельная группа таблиц
  обслуживает циклические испытания (`cycling_sessions`, `cycling_datapoints`,
  `cycling_cycle_summary`);
- **Развитие схемы:** только через **forward-only SQL-миграции** — без `DROP
  TABLE` и без потенциально-разрушительных `ALTER`;
- **Учёт применённых миграций:** таблица `public.schema_migrations` —
  authoritative ledger. По состоянию на 25.05.2026 — около 50 миграций
  (последняя — `d040_add_coated_thickness_fields.sql`);
- Часть защитных правил реализована на уровне БД (триггеры и check-constraints):
  валидация стека электродов аккумулятора, контроль M2M-связей проекта,
  ограничения форм-факторов.

### Аналитика и обработка данных

**Расчётная и workflow-ориентированная** (vanilla v1 + V2):

- расчёт массовых долей и масс компонентов рецепта;
- расчёт параметров электродов по фактическим измерениям;
- расчёт ёмкости электродов и аккумуляторов;
- подсказки по компоновке стека электродов;
- раздельный учёт технологических настроек и фактических измерений (например,
  зазоры нанесения отдельно от толщин после нанесения/сушки до каландрирования);
- печатные отчёты по объектам.

**Циклические испытания** (V2): интерактивные графики ёмкости заряда/разряда,
кулоновской эффективности, средних напряжений, энергоэффективности по
циклам — с возможностью наложения нескольких сессий и сохранения пользовательских
стилевых пресетов (цвета, маркеры, толщины линий). Per-cycle сводки доступны
как через UI, так и через API; экспорт в XLSX даёт структурированный набор
листов для дальнейшего анализа во внешних инструментах.

Каждая сессия циклирования привязана к конкретному аккумулятору в БД —
это замыкает цепочку прослеживаемости «материал → … → испытания»,
описанную в §1.

## 5. Безопасность, авторизация и контроль пользователей

### Авторизация и контроль доступа

- **Авторизация:** JWT Bearer-токены; срок жизни 8 часов (длина смены);
- **Пароли:** хешируются `bcrypt`, 10 раундов; в открытом виде не хранятся;
- **Роли:** `admin`, `lead`, `employee`; права разграничены на уровне
  middleware (`requireRole`);
- **Защита от перебора:** скользящее окно 10 неуспешных входов за 60 минут,
  блокировка на 1 час. Источник истины — `auth_log` (append-only); защита от
  race condition — через `pg_advisory_xact_lock` в одной транзакции с проверкой
  пароля;
- **Инвалидация токенов:** колонка `users.token_version` — при смене пароля и
  административном сбросе номер версии увеличивается, все ранее выданные
  токены отвергаются (HTTP 401);
- **Real-time контроль активности:** на каждом запросе middleware проверяет
  `users.active`; при деактивации учётной записи активная сессия пользователя
  отклоняется немедленно (HTTP 403), не дожидаясь истечения JWT;
- **Защита от user enumeration:** одинаковые сообщения об ошибках логина для
  несуществующего пользователя и неверного пароля;
- **Управление паролями:** пользователь меняет пароль через `change-password`
  (с подтверждением текущего); администратор может выдать временный пароль
  через `admin-reset-password/:userId` — пользователь обязан сменить его при
  следующем входе;
- **Аудит-журнал:** append-only таблица `auth_log` фиксирует все события входа
  (успех/отказ с причиной), регистрацию, смену пароля, административный сброс,
  активацию/деактивацию учётной записи; журнал не обновляется и не удаляется.

### Сетевая защита приложения

- **`BIND_HOST`** — настраиваемый интерфейс прослушивания (`0.0.0.0` /
  `127.0.0.1` / явный LAN-IP). Для production рекомендуется привязка к
  конкретному LAN-IP;
- **`ALLOWED_IPS`** — опциональный CIDR-allowlist для `/api/*`; при настройке
  отклоняет запросы с не-разрешённых адресов (HTTP 403);
- **Rate limiting** — 300 запросов в минуту на `/api/*` с одного IP;
- **HTTP-заголовки безопасности через `helmet`:** X-Frame-Options,
  X-Content-Type-Options, Referrer-Policy, Strict-Transport-Security,
  Cross-Origin-* и пр. (CSP временно отключена — отдельный refactor с
  nonce/hash);
- **Cache-control: no-store** на всех `/api/*` ответах.

### Внешние сетевые взаимодействия отсутствуют

Решение **не обращается ни к каким внешним API, облачным сервисам или
интернет-ресурсам.** В перечне зависимостей нет HTTP-клиентов для внешних
сервисов. Все коммуникации происходят между браузером пользователя и сервером
решения в пределах сетевого контура, согласованного с IT/Гринатомом. Это
позволяет разместить решение в **полностью изолированной сети (КСПД) без
выхода в интернет**.

### Что не реализовано на уровне приложения и должно учитываться в инфраструктуре

- **Многофакторная аутентификация (MFA)** — в текущей версии не реализована.
  При требовании политики площадки MFA может быть добавлена внешними
  средствами (reverse proxy с OAuth/OIDC, LDAP/AD-интеграция) без изменения
  серверной логики решения;
- **Шифрование резервных копий «в покое»** — на уровне `scripts/backup.js` не
  реализовано (файл — несжатый `pg_dump` custom format или текстовый
  `pg_dump --format=plain`). Шифрование рекомендуется обеспечить на уровне
  файловой системы / хранилища (BitLocker, LUKS, шифрованный том);
- **HTTPS/TLS-терминация** — на уровне приложения не реализована (Express
  слушает HTTP). HTTPS обеспечивается reverse proxy: nginx (Linux) или IIS
  с URL Rewrite (Windows); готовые конфигурации — в «05. Руководстве
  системного программиста» §3.5;
- **Приватность файлов в `uploads/`** — каталог сейчас раздаётся Express'ом
  статически; защита по токену запланирована отдельной задачей. До её
  внедрения mitigation — сетевая изоляция контура (`ALLOWED_IPS`, отсутствие
  внешних сетевых взаимодействий).

Открытые вопросы по безопасности (политика паролей, MFA, шифрование «в
покое», срок хранения журналов, HTTPS-сертификат, регламент резервирования)
сведены в таблицу §9.

### Ожидаемая нагрузка и рост данных (оценочные)

- **Одновременных пользователей:** оценочно до полутора десятков сотрудников
  Центра ХИТ в одной смене;
- **Прирост структурированных данных в БД:** порядка десятков мегабайт в месяц;
- **Прирост файлового хранилища `uploads/`:** основная статья роста — исходные

  гигабайт в год при текущем темпе R&D;
- **Прирост `sql_backups/`:** с настроенной 30-дневной ротацией стабилизируется
  в установившемся режиме (порядка нескольких десятков гигабайт).

Оценки приведены для **текущей фазы развития решения**; при масштабировании
функциональности и подключении дополнительных подразделений требуется
пересмотр.

## 7. Сетевая доступность и взаимодействие с базой

### Прямой ответ на вопрос п.7 руководителя

Для обычных пользователей **достаточно доступа через браузер** к веб-интерфейсу
решения:

- Если в КСПД доступен **браузер на терминальном сервере (RDP)** — этого
  достаточно для пилотного использования. Файловый обмен через ту же
  RDP-сессию (даже не самый удобный) допустим для пилота.
- **Прямой LAN-доступ к внутреннему HTTP(S)-адресу решения с лабораторных
  устройств** предпочтительнее на этапе масштабирования: операторы смогут
  вводить данные с ноутбуков или планшетов непосредственно во время
  приготовления лент, нарезки электродов и сборки аккумуляторов — без
  переключения между терминальной и лабораторной средами.

### Сетевая модель

- **HTTP(S)-порт веб-интерфейса:** по умолчанию **3003**, конфигурируется
  через `PORT` (согласовывается с IT);
- **Порт PostgreSQL:** **5432**; доступ ограничен административной подсетью
  или явным CIDR;
- **`BIND_HOST`:** конфигурируется (рекомендуется явный LAN-IP в production);
- **Доменное имя сервера:** согласовывается с IT/Гринатомом (например,
  `lims-cht.renera.local`); работа по IP-адресу или через `hosts` лабораторных
  машин допустима для пилота при отсутствии корпоративного DNS.

### Файловый обмен

Для решения важно не просто **передать файл**, а **связать его с конкретной
записью**: материалом, лентой, партией электродов, аккумулятором. Все вложения
загружаются и скачиваются через веб-интерфейс — у каждого есть запись в БД с
автором, временем загрузки и связью с лабораторным объектом. Это обеспечивает
прослеживаемость происхождения файла независимо от срока давности.

### Прямой доступ к БД

Только для администратора сервера и сопровождающего разработчика — для
миграций, резервного копирования, восстановления и точечной диагностики через
`psql` в рамках согласованной административной процедуры.

## 9. Предложения по организации инфраструктуры

### Действия при развёртывании пилота

Помимо установки ПО (PostgreSQL 16.x, Node.js 22 LTS, приложение
«Протоколы сборки лаборатории ХИТ»),
требуется со стороны IT/Гринатома:

1. Организовать место и регламент хранения резервных копий БД и каталога
   `uploads/` (см. инструментарий ниже).
2. Выпустить HTTPS-сертификат и настроить reverse proxy (nginx или IIS).
3. Выпустить production-секреты (`JWT_SECRET`, пароль БД).
4. Согласовать сетевую модель (порты, IP-allowlist, доменное имя).

### Что уже реализовано в комплекте

- **Резервное копирование** — кроссплатформенный скрипт `scripts/backup.js`
  (Windows и Linux): pre-flight checks, post-backup verification через
  `pg_restore --list`, lock-файл против параллельного запуска, append-only
  журнал `backup.log`. Параметры: `--format=plain|custom`, `--keep-days=N`
  (по умолчанию 30), `--restore`, `--list`, `--verify`. Команды npm:
  `npm run backup`, `npm run backup:plain`, `npm run backup:list`,
  `npm run backup:verify`, `npm run restore`. Готовые шаблоны заданий для
  Windows Task Scheduler и Linux cron — в «05. Руководстве сисадмина» §5.1.
- **HTTPS reverse proxy** — готовые конфигурации nginx и IIS (URL Rewrite) в
  «05. Руководстве сисадмина» §3.5.

## Краткое резюме

«Протоколы сборки лаборатории ХИТ» — внутрисетевое веб-приложение (PostgreSQL + Node.js/Express +
браузер). Пригодно для размещения в изолированной сети (КСПД) — внешний
интернет не требуется.

- **Пользователи** — через браузер (RDP допустимо, прямой LAN
  предпочтительнее); **прямой доступ к БД** — только для администраторов.
- **Функциональность:** workflow «материал → лента → электрод → аккумулятор»
  реализован в vanilla v1 (production); модуль циклических испытаний — в
  V2 (использует ту же серверную инфраструктуру).
- **Аппаратные требования:** от 8 ГБ ОЗУ и 100 ГБ SSD (минимум); от 16 ГБ
  ОЗУ и 500 ГБ NVMe (рекомендуемо).
- **Инструментарий резервирования и HTTPS reverse proxy** реализован
  (см. «05. Руководство сисадмина»); открытые вопросы к IT/Гринатому —
  в таблице §9.

Подробные сведения и точные количественные характеристики — в комплекте
ЕСПД v0.1.16, прилагается отдельно по требованию.
