# 1. Общие сведения

## 1.1. Назначение программы

Программное обеспечение **ЛИМС-ХИТ** (лабораторная информационно-управляющая система «Химические источники тока») — корпоративное веб-приложение для автоматизации учёта и обработки лабораторных данных R&D-процессов Центра химических источников тока ООО «РЭНЕРА»: разработка электродных материалов, электролитов, сепараторов, ячеек и батарейных модулей различных электрохимических систем. Подробное описание — в «ТЗ» (BADB.00001-01) и «Описании программы» (BADB.00001-01 13 01).

## 1.2. Требования к квалификации системного программиста

Для выполнения установки, настройки и поддержки программы системный программист должен обладать:

- Навыками работы с ОС Windows (установка ПО, управление службами через `services.msc`, настройка Task Scheduler, базовое владение PowerShell и командной строкой `cmd`). При альтернативном развёртывании — навыками Linux (Ubuntu 22.04 LTS или совместимая).
- Базовыми знаниями PostgreSQL: создание баз, пользователей, ролей; выполнение SQL-скриптов; работа с `pg_dump.exe` / `pg_restore.exe` (или pgAdmin 4).
- Базовыми знаниями Node.js: установка через MSI-инсталлятор с официального сайта; работа с `npm`.
- Навыками работы с Git: клонирование, переключение веток, проверка статуса репозитория (в Windows — Git for Windows с `git-bash` либо встроенная Git-поддержка в PowerShell).
- Пониманием принципов сетевой безопасности: настройка брандмауэра Windows Defender Firewall, IP-allowlist, HTTPS, reverse proxy.

## 1.3. Минимальные требования к серверу

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| Процессор | 4 ядра, x86_64, 2.0 ГГц | 8 ядер, 2.5 ГГц |
| Оперативная память | 8 ГБ | 16 ГБ |
| Накопитель | SSD, 100 ГБ свободных | NVMe SSD, от 500 ГБ |
| Сеть | 100 Мбит/с Ethernet или Wi-Fi в зоне корпоративного маршрутизатора | 1 Гбит/с Ethernet |
| Операционная система (основной вариант) | Windows 10 Pro 64 бит (версия 22H2 и новее) | Windows 11 Pro 64 бит / Windows Server 2022 |
| Операционная система (альтернативный) | Ubuntu 22.04 LTS | Ubuntu 24.04 LTS |
| Источник бесперебойного питания (ИБП) | — | Рекомендуется для защиты БД от некорректного выключения |

# 2. Структура программы

## 2.1. Дерево каталогов

Корневой каталог развёртывания:

- **Windows (основной вариант):** `C:\LIMS-CCS\` или `C:\Program Files\LIMS-CCS\` (требует прав администратора; предпочтительнее первый вариант без пробелов в пути для совместимости с Python/Node).
- **Linux (альтернативный):** `/opt/badb/` или `/home/badb/BADB_main/`.

Ниже приведена структура каталогов; абсолютный корневой путь — любой, структура относительно него одинакова на всех ОС.

```
BADB_main/
├── app.js                  -- фабрика Express-приложения
├── server.js               -- запуск HTTP-сервера
├── db.js, db/pool.js       -- пул PostgreSQL
├── package.json            -- зависимости серверной части
├── package-lock.json
├── config/
│   ├── index.js            -- основной конфиг
│   └── navigation.js       -- структура меню
├── routes/                 -- маршруты API (21 файл)
├── services/               -- сервисный слой бизнес-логики (30 файлов)
├── middleware/             -- auth, validate, trackChanges, errorHandler, ipAllowlist
├── contracts/schemas/      -- JSON-схемы валидации
├── migrations/             -- SQL-миграции (41 файл, forward-only, включая d032)
├── migrations_ASCII/       -- ASCII-копии SQL-миграций (41 файл)
├── client-web/             -- Vue parity/handoff-поверхность
│   ├── src/
│   ├── package.json
│   └── vite.config.js
├── public/                 -- текущий vanilla v1 клиент и печатные отчёты
├── uploads/                -- загруженные файлы (электрохимия, циклирование)
├── scripts/
│   ├── backup.js           -- резервное копирование
│   ├── parse_cycling.py    -- парсер циклирования
│   └── launchd/            -- плисты для запуска службы (только разработка)
├── sql_backups/            -- резервные копии БД
├── sql_scripts/            -- служебные SQL-скрипты
└── .env                    -- переменные окружения (не под системой контроля версий)
```

**Назначение каталога `services/`** — модули с бизнес-логикой, общей для нескольких маршрутов или требующей обёртки в транзакцию. Маршрут `routes/<entity>.js` вызывает функции из `services/<entity>Service.js` и преобразует результат в HTTP-ответ; сервис не знает об HTTP. Примеры: `tapeCatalogService.js` (CRUD-операции над лентами), `tapeStepSaveService.js` (диспетчер сохранения этапов процесса), `batteryElectrodeSourceService.js` (источники электродов с поддержкой транзакций), `batteryElectrodeStackService.js` (валидация стека и trigger-safe paired order `A1, C1, A2, C2` под `d031` с сохранением `position_index`), `batteryLifecycleService.js` (guided delete, hard blockers, electrode disposition, audit), `tapeProjectService.js` / `electrodeBatchProjectService.js` / `batteryProjectService.js` (связи «многие ко многим» с проектами через таблицы `tape_projects` / `electrode_cut_batch_projects` / `battery_projects` — миграции d028/d029/d030).

## 2.2. Используемые порты

| Порт | Назначение | Обязательность |
|---|---|---|
| 3003 | HTTP(S) API + текущий vanilla v1 статический клиент | Обязателен |
| 5173 | Vite dev-сервер Vue parity-поверхности | Только в режиме разработки |
| 5432 | PostgreSQL (стандартный). В dev-Docker используется хост-порт 5434 (сопоставлен с 5432 контейнера) | Настраивается стандартной libpq-переменной `PGPORT` |
| 8080 | pgAdmin | Опционально, только для администрирования |

## 2.3. Внешние зависимости

Программа **не обращается** к внешним сетевым ресурсам при работе. Все сборочные зависимости (npm-пакеты) загружаются один раз при установке и не требуют доступа в Интернет во время эксплуатации.

### 3.1.6. Настройка переменных окружения

Переменные задаются стандартными средствами операционной системы или через файл `.env` в корневом каталоге (**Windows:** `C:\LIMS-CCS\.env`; **Linux:** `/opt/badb/.env`). Node.js 22 читает `.env` только при запуске с флагом `--env-file=.env`; при запуске как службы предпочтительно задавать переменные в конфигурации службы или явно добавить этот флаг к команде запуска.

Список применяемых переменных:

```ini
# === Прикладные переменные (читаются в config/index.js) ===

# Порт HTTP-сервера (по умолчанию 3003)
PORT=3003

# Имя пользователя и базы PostgreSQL для подключения через pg.Pool
# (host/port/password подставляются из стандартных libpq-переменных
#  PGHOST/PGPORT/PGPASSWORD — см. блок ниже)
DB_USER=badb_app
DB_NAME=badb_app_v1

# Интерфейс прослушивания HTTP-сервера
#   0.0.0.0      — слушать на всех сетевых интерфейсах сервера
#   <IP сервера> — слушать только на конкретном интерфейсе LAN (рекомендуется для production)
#   127.0.0.1    — только loopback (для разработки)
BIND_HOST=0.0.0.0

# Секрет для подписи JWT (обязательно для production; минимум 32 случайных байта в base64)
# Windows: [Convert]::ToBase64String((1..48 | ForEach-Object { [byte](Get-Random -Max 256) }))
# Linux:   openssl rand -base64 48
# Проверка на старте: server.js откажет в production-запуске, если JWT_SECRET не задан.
JWT_SECRET=<длинная_случайная_строка>

# Опциональный IP-allowlist (CIDR через запятую). Пустое значение или
# отсутствие переменной — фильтр отключён, все клиенты допускаются.
# ALLOWED_IPS=127.0.0.1,10.0.0.0/8,192.168.0.0/16

# Опциональное включение redirect-режима HTML -> Vue для parity-проверок.
# По умолчанию текущие vanilla v1 страницы доступны напрямую.
# VUE_HTML_REDIRECTS=true

# === Стандартные переменные libpq (читаются клиентом PostgreSQL pg) ===

# Хост и порт PostgreSQL (по умолчанию localhost:5432)
PGHOST=localhost
PGPORT=5432

# Пароль пользователя БД. Альтернатива — файл `.pgpass` (Linux) или
# Windows Credential Manager. Этот вариант предпочтительнее, чем
# хранить пароль в .env.
PGPASSWORD=<надёжный_пароль>
```

**Замечания.**

- `JWT_EXPIRY` (срок жизни токена — 8 часов) и `BCRYPT_ROUNDS` (10) — фиксированные значения в `config/index.js`, не задаются переменной окружения.
- `NODE_ENV` — стандартная переменная Node.js. В `server.js` используется для production-инвариантов: при `NODE_ENV=production` сервер отказывает старт, если `JWT_SECRET` не задан или `AUTH_BYPASS=true`; Express и npm-зависимости также могут менять поведение в зависимости от значения. Для production устанавливать `NODE_ENV=production`.
- `AUTH_BYPASS=true` + `BYPASS_LOGIN=<логин>` — режим отладки с автоматическим входом, **только** для разработки. На продуктивном сервере не задавать.

**Защита файла `.env`.**

- Файл **не должен** попадать в систему контроля версий (`.gitignore` уже содержит запись).
- **Windows:** в свойствах файла снять разрешения на чтение у стандартных групп и оставить только учётной записи, от имени которой запускается служба (Properties → Security → Advanced → Disable inheritance → Remove all → Add account; либо через PowerShell `icacls`).
- **Linux:** установить права `chmod 600 .env`.

### 3.1.7. Применение миграций

Миграции находятся в каталогах `migrations/` и `migrations_ASCII/` и применяются в порядке имён. Для Windows/lab развёртывания допускается использовать ASCII-версии SQL-файлов, если путь или консольная кодировка мешает применению основного файла.

**Windows (PowerShell):**

```powershell
cd C:\LIMS-CCS
$psql = "C:\Program Files\PostgreSQL\16\bin\psql.exe"

Get-ChildItem "migrations\*.sql" | Sort-Object Name | ForEach-Object {
    Write-Host "Applying: $($_.Name)"
    & $psql -U badb_app -d badb_app_v1 -h localhost -f $_.FullName
}
```

**Linux (bash):**

```bash
cd /opt/badb

for f in $(ls migrations/*.sql | sort); do
  echo "Applying: $f"
  psql -U badb_app -d badb_app_v1 -h localhost -f "$f"
done
```

*На текущий момент автоматизированного runner-а миграций (`node-pg-migrate`, `dbmate`, `umzug` и т.п.) в проекте **нет**. Миграции применяются вручную в порядке имён, как показано выше. Авторитетный ledger применённых миграций — таблица `public.schema_migrations`, созданная и backfill-нутая `d032_create_schema_migrations_table.sql`. Файлы `migrations_log.txt` в `migrations/` и `migrations_ASCII/` являются human checkpoint notes only.*

Для vanilla v1 pilot readiness обязательно отдельно подтвердить на Windows/lab БД:

1. `schema_migrations` содержит текущие stream counts:

```sql
SELECT migration_stream, count(*)
  FROM schema_migrations
 GROUP BY migration_stream
 ORDER BY migration_stream;
```

Ожидаемый результат: `dima = 21`, `dalia = 20`.

2. `d031_harden_battery_stack_validate_trigger.sql` применён:

```sql
SELECT
  (position('anode_count = cathode_count + 1' in pg_get_functiondef('public.validate_battery_stack()'::regprocedure)) > 0) AS allows_extra_anode,
  (position('cathode_count = anode_count + 1' in pg_get_functiondef('public.validate_battery_stack()'::regprocedure)) > 0) AS allows_extra_cathode,
  (position('TG_OP = ''UPDATE''' in pg_get_functiondef('public.validate_battery_stack()'::regprocedure)) > 0) AS handles_update;
```

Ожидаемый результат: `allows_extra_anode = true`, `allows_extra_cathode = false`, `handles_update = true`.

### 3.1.8. Начальный ввод данных

Для чистой установки необходимо создать первого администратора. На текущий момент скрипт автоматической регистрации не предоставляется; используется прямая SQL-вставка.

**Шаг 1.** Сгенерировать bcrypt-хеш пароля.

## 3.4. Запуск как системной службы

Сервер должен запускаться автоматически при включении серверной машины. Варианты реализации зависят от операционной системы.

### 3.4.1. Windows — через NSSM (Non-Sucking Service Manager)

**NSSM** — надёжная утилита для оборачивания произвольной программы в Windows-службу. Распространяется как один исполняемый файл, работает без установщика.

**Установка:**

1. Скачать NSSM с официального сайта (`nssm.cc`) на машине с Интернетом, перенести на сервер.
2. Распаковать. Скопировать `nssm.exe` в `C:\Windows\System32\` или в `C:\LIMS-CCS\bin\`.

**Регистрация службы:**

Открыть PowerShell от имени администратора и выполнить:

```powershell
# Зарегистрировать службу "LIMS-CCS".
# Если переменные окружения заданы в системе, достаточно server.js.
# Если используется файл .env, добавить --env-file.
nssm install LIMS-CCS "C:\Program Files\nodejs\node.exe" "--env-file=C:\LIMS-CCS\.env" "C:\LIMS-CCS\server.js"

# Указать рабочий каталог
nssm set LIMS-CCS AppDirectory "C:\LIMS-CCS"

# Перенаправить журналы
New-Item -ItemType Directory -Force -Path "C:\LIMS-CCS\logs"
nssm set LIMS-CCS AppStdout "C:\LIMS-CCS\logs\server.log"
nssm set LIMS-CCS AppStderr "C:\LIMS-CCS\logs\error.log"

# Автоматический перезапуск при сбое
nssm set LIMS-CCS AppExit Default Restart
nssm set LIMS-CCS AppRestartDelay 5000

# Режим запуска: автоматически при старте системы
nssm set LIMS-CCS Start SERVICE_AUTO_START

# Запустить службу
nssm start LIMS-CCS
```

**Управление службой:**

```powershell
# Статус
sc query LIMS-CCS

# Запуск / остановка / перезапуск
nssm start LIMS-CCS
nssm stop LIMS-CCS
nssm restart LIMS-CCS

# Удаление (при переустановке)
nssm remove LIMS-CCS confirm
```

**Просмотр журналов:**

```powershell
Get-Content C:\LIMS-CCS\logs\server.log -Tail 50 -Wait
```

**Альтернативный вариант без NSSM:** пакет `node-windows` (установка `npm install -g node-windows`; пример установщика сервиса — `scripts/windows/install-service.js`, *@уточнить наличие такого скрипта*).

### 3.4.2. Linux — через systemd

Создайте файл `/etc/systemd/system/badb.service`:


## 3.5. Настройка обратного прокси (HTTPS) — опционально

В текущем сценарии развёртывания (сервер Windows, доступ коллег по локальной сети через маршрутизатор) прямой HTTP-доступ на порт 3003 может считаться достаточным, если политика безопасности ООО «РЭНЕРА» это допускает. Для повышения безопасности (шифрование трафика в LAN) возможно добавление reverse proxy с HTTPS-терминацией.

### 3.5.1. Windows — через IIS + URL Rewrite (рекомендуется)

Установить роль IIS с модулями URL Rewrite и Application Request Routing (ARR):

```powershell
# Роль IIS (включая URL Rewrite)
Install-WindowsFeature Web-Server, Web-Mgmt-Console, Web-Asp-Net45

# Скачать и установить расширения (на машине с Интернетом):
#   - URL Rewrite Module 2.1 (https://www.iis.net/downloads/microsoft/url-rewrite)
#   - Application Request Routing 3.0
# Перенести MSI на сервер и установить.
```

Включить ARR в прокси-режим: **IIS Manager → сервер → Application Request Routing Cache → Server Proxy Settings → Enable proxy**.

В IIS создать новый сайт с привязкой к HTTPS-порту 443 и SSL-сертификатом, затем в конфигурации URL Rewrite добавить правило, перенаправляющее все входящие запросы на `http://localhost:3003`.

Пример `web.config` сайта:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
  <system.webServer>
    <rewrite>
      <rules>
        <rule name="LIMS-CCS Reverse Proxy" stopProcessing="true">
          <match url="(.*)" />
          <action type="Rewrite" url="http://localhost:3003/{R:1}" />
        </rule>
      </rules>
    </rewrite>
    <security>
      <requestFiltering>
        <requestLimits maxAllowedContentLength="20971520" />
      </requestFiltering>
    </security>
  </system.webServer>
</configuration>
```

### 3.5.2. Windows — альтернатива через nginx for Windows

Скачать `nginx-1.x-windows.zip` с `nginx.org`, распаковать в `C:\nginx`, создать конфигурацию `C:\nginx\conf\nginx.conf` (см. пример для Linux ниже — конфигурация идентична, пути к сертификатам адаптировать к Windows), запустить как службу через NSSM.

### 3.5.3. Linux — через nginx

```nginx
upstream badb_backend {
    server 127.0.0.1:3003;
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name <имя-сервера>;

    ssl_certificate     /etc/ssl/certs/badb.crt;
    ssl_certificate_key /etc/ssl/private/badb.key;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    client_max_body_size 20M;

    location / {
        proxy_pass http://badb_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}

server {
    listen 80;
    server_name <имя-сервера>;
    return 301 https://$server_name$request_uri;
}
```

# 5. Дополнительные возможности

## 5.1. Резервное копирование

### 5.1.1. Принципы и стандарты процедуры

Программа содержит собственный кроссплатформенный скрипт резервного копирования — `scripts/backup.js`. Скрипт реализует принятые в промышленной эксплуатации стандарты:

- **Pre-flight checks** — проверка соединения с БД и свободного места на диске перед запуском;
- **Post-backup verification** — проверка целостности dump-файла через `pg_restore --list`;
- **Контрольная сумма SHA-256** каждого дампа — для проверки целостности при переносе между носителями;
- **Manifest** — сопроводительный файл с метаданными (версия PostgreSQL, список таблиц, количество записей в каждой);
- **Lock-файл** — защита от параллельного запуска двух процессов резервного копирования;
- **Append-only журнал** — файл `backup.log` для аудита всех операций копирования и восстановления;
- **Поддержка ротации** — удаление копий старше заданного возраста с гарантией минимального количества хранимых копий.

### 5.1.2. Ручное создание резервной копии

**Windows (PowerShell из корневого каталога установки):**

```powershell
cd C:\LIMS-CCS
npm run backup               # custom format (бинарный, сжатый)
npm run backup:plain         # plain SQL (текстовый дамп)
```

**Linux:**

```bash
cd /opt/badb
npm run backup
npm run backup:plain
```

Файл сохраняется в каталоге `sql_backups\auto\` (Windows) или `sql_backups/auto/` (Linux) с именем вида:

```
badb_<YYYYMMDD>_<HHMMSS>.dump         # custom format
badb_<YYYYMMDD>_<HHMMSS>.sql          # plain format
```

Вместе с файлом сохраняются:

- `*.sha256` — файл с контрольной суммой;
- `*.manifest.json` — метаданные копии (версия БД, перечень таблиц, даты);
- `backup.log` — обновляется (append-only) с записью о проведённой операции.

### 5.1.3. Автоматическое (регулярное) резервное копирование

#### Windows — через планировщик задач (Task Scheduler)

**Вариант 1: через графический интерфейс.**

1. Открыть **Планировщик заданий** (Task Scheduler).
2. Создать задачу → закладка **«Общие»**:
   - Имя: `LIMS-CCS daily backup`;
   - Выполнять для всех пользователей;
   - Выполнять с наивысшими правами;
   - Настроить для Windows 10 / 11 / Server 2019 / 2022.
3. Закладка **«Триггеры»** → Создать:
   - Ежедневно, время `02:00`, повторять каждый день.
4. Закладка **«Действия»** → Создать:
   - Действие: «Запуск программы»;
   - Программа/сценарий: `C:\Program Files\nodejs\npm.cmd`
   - Аргументы: `run backup`
   - Рабочая папка: `C:\LIMS-CCS`
5. Закладка **«Условия»**:

### 5.4.2. Сброс пароля пользователя

**Способ 1 (рекомендуемый) — через API-маршрут `POST /api/auth/admin-reset-password/:userId`.**

Маршрут доступен только пользователям с ролью `admin`. Системный программист или администратор системы получает JWT через обычный вход и выполняет запрос через инструмент веб-разработчика браузера или через `curl`:

```bash
curl -X POST http://<сервер>:3003/api/auth/admin-reset-password/42 \
  -H "Authorization: Bearer <JWT-токен_администратора>" \
  -H "Content-Type: application/json" \
  -d '{"new_password":"<временный_пароль>"}'
```

Маршрут выполняет: хеширование пароля через bcrypt (10 раундов, как при создании пользователя); обновление `users.password_hash`; инкремент `users.token_version` (инвалидирует все активные токены пользователя); запись события `password_reset_by_admin` в `auth_log` с указанием инициатора (полей `user_id` и `login` администратора в `details`).

После сброса пользователь должен войти в систему с временным паролем и сменить пароль через маршрут смены пароля (`POST /api/auth/change-password-public` при сценарии временного пароля или `POST /api/auth/change-password` для штатной смены).

**Способ 2 (fallback) — прямой SQL-запрос к БД.**

Применяется, если веб-интерфейс недоступен (например, при первичной настройке или после сбоя):

**Windows (PowerShell):**

```powershell
$PASS_HASH = node -e "console.log(require('bcryptjs').hashSync('<новый-пароль>',10))"
$psql = "C:\Program Files\PostgreSQL\16\bin\psql.exe"
& $psql -U badb_app -d badb_app_v1 -h localhost -c `
    "UPDATE users SET password_hash='$PASS_HASH', token_version = token_version + 1 WHERE lower(login) = lower('jsmith');"
```

**Linux:**

```bash
PASS_HASH=$(node -e "console.log(require('bcryptjs').hashSync('<новый-пароль>',10))")
psql -U badb_app -d badb_app_v1 -h localhost -c \
  "UPDATE users SET password_hash='$PASS_HASH',
                    token_version = token_version + 1
   WHERE lower(login) = lower('jsmith');"
```

Инкремент `token_version` инвалидирует все активные токены пользователя и потребует повторного входа. При использовании fallback-способа событие `password_reset_by_admin` в `auth_log` **не записывается** — для аудита рекомендуется добавить запись вручную:

```sql
INSERT INTO auth_log (user_id, login, event, details)
SELECT user_id, login, 'password_reset_by_admin',
       jsonb_build_object('reset_by', 'system_programmer', 'method', 'direct_sql')
FROM users WHERE lower(login) = lower('jsmith');
```

### 5.4.3. Блокировка пользователя

```sql
UPDATE users SET active = false,
                 token_version = token_version + 1
 WHERE lower(login) = lower('jsmith');
```

Поле `active` (boolean) уже присутствует в таблице `users` — используется для деактивации учётной записи без её удаления. Инкремент `token_version` инвалидирует все текущие токены заблокированного пользователя.

### 5.4.4. Разблокировка после превышения попыток входа

Счётчик неудачных попыток входа определяется **по записям в `auth_log`** (не по отдельной колонке в `users`) с помощью скользящего окна. Конкретный SQL-запрос в `routes/auth.js`:

```sql
SELECT COUNT(*) FROM auth_log
 WHERE login = $1
   AND event = 'login_failed'
   AND created_at > now() - make_interval(mins => $2)
```

Параметры: `$1` — логин, `$2` — длительность окна в минутах (`config.rateLimit.lockoutWindowMinutes`, по умолчанию 60). Лимит — `config.rateLimit.maxFailedAttempts` (по умолчанию 10). Запрос выполняется внутри транзакции под `pg_advisory_xact_lock`, что исключает гонку условий при одновременных параллельных попытках.

Способы «разблокировки» пользователя, превысившего лимит:

1. **Ожидание (рекомендуемый способ).** Блокировка автоматически снимается, как только все неудачные попытки выходят за пределы скользящего окна — то есть через `lockoutWindowMinutes` минут после **первой** попытки в текущем окне. Пользователь повторяет попытку и попадает в обычный поток входа.

2. **Сброс пароля администратором** (см. §5.4.2, способ 1). После выпуска нового временного пароля пользователь логинится с ним; срабатывает успешная попытка, но **счётчик неудач не очищается** — старые записи `login_failed` остаются в `auth_log` (таблица append-only). Если пользователь снова допустит ошибку, лимит может сработать повторно. Администратору следует напомнить пользователю записать новый пароль в безопасном месте перед попыткой входа.

3. **Прямое удаление записей из `auth_log` запрещено** — таблица append-only по требованиям аудита (документ 02 «Описание программы», §3.8.5 «Цепочка аудита»). Системному программисту не следует обходить это правило даже при срочной необходимости — это нарушит цепочку аудита. Корректное решение — ожидание окна или сброс пароля.

## 5.6. Диагностика проблем

### 5.6.1. Сервер не запускается

| Симптом | Диагностика | Действие |
|---|---|---|
| Ошибка «EADDRINUSE» | Порт 3003 занят | `lsof -i :3003` — найти конкурирующий процесс; остановить или изменить `PORT` |
| Ошибка подключения к БД | PostgreSQL не запущен / неверные креденшелы | `sudo systemctl status postgresql`; проверить `.env` |
| «JWT_SECRET is required» | Не задана переменная | Установить в `.env` |
| «AUTH_BYPASS is set in production» | Остался dev-флаг | Убрать `AUTH_BYPASS` из `.env` |

### 5.6.2. Сервер работает, но запросы медленные

| Симптом | Диагностика | Действие |
|---|---|---|
| Высокий CPU Node | Запрос с неоптимальным планом | Проверить медленные запросы в журнале PostgreSQL |
| Высокий CPU PostgreSQL | Нет индексов / большой размер таблиц | `EXPLAIN ANALYZE` на медленные запросы; создать индексы |
| Высокое потребление памяти | Большой пул соединений | Настроить `max_connections` в `postgresql.conf` |

### 5.6.3. Ошибки клиента в браузере

| Симптом | Диагностика | Действие |
|---|---|---|
| «Сервер недоступен» | CORS / сеть / сервер лежит | Проверить доступность API: `curl http://<хост>:3003/api/auth/me` |
| «Сессия истекла» | Токен просрочен или инвалидирован | Перезайти |
| «Форма содержит ошибки» | Валидация JSON Schema | Проверить консоль браузера: сервер возвращает детали в поле `details` |
| «409 Conflict» | Оптимистичная блокировка | Обновить страницу; повторить операцию |

## 5.7. Специальные ситуации

### 5.7.1. Включение Vue redirect-режима для parity-проверки

По умолчанию vanilla HTML-страницы из `public/` доступны напрямую и являются текущей release-candidate поверхностью. Для явной проверки optional redirects HTML → Vue можно включить режим:

```bash
VUE_HTML_REDIRECTS=true npm start
```

**Не оставлять эту настройку в продуктивной среде.**

### 5.7.2. Rate limiting при тестировании

Текущий код не содержит отдельной переменной для отключения `express-rate-limit`. Нагрузочные проверки выполняются с учётом лимита 300 запросов в минуту на IP или в изолированной тестовой конфигурации, согласованной с разработчиком.

### 5.7.3. Принудительная инвалидация всех токенов

При подозрении на компрометацию `JWT_SECRET`:

1. Сгенерировать новый секрет.
2. Обновить `.env`.
3. Перезапустить сервис.

После этого все существующие токены становятся невалидными, пользователи будут вынуждены войти заново.

## 6.3. Диагностические запросы к БД

### Количество пользователей и активность

```sql
SELECT role, count(*) FROM users GROUP BY role;

SELECT date_trunc('day', occurred_at) as day, count(*)
  FROM auth_log
 WHERE event = 'login_success'
   AND occurred_at > now() - interval '7 days'
 GROUP BY day ORDER BY day;
```

### Подозрительная активность (неудачные попытки)

```sql
SELECT ip_address, count(*) as attempts, max(occurred_at) as last_attempt
  FROM auth_log
 WHERE event = 'login_failed'
   AND occurred_at > now() - interval '1 hour'
 GROUP BY ip_address
 ORDER BY attempts DESC
 LIMIT 20;
```

### Размеры таблиц

```sql
SELECT schemaname, tablename,
       pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) as size
  FROM pg_tables
 WHERE schemaname = 'public'
 ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
 LIMIT 10;
```

### Активные соединения

```sql
SELECT pid, usename, state, query_start, query
  FROM pg_stat_activity
 WHERE datname = 'badb_app_v1'
   AND state != 'idle';
```
