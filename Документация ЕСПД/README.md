# ЛИМС-ХИТ — Комплект технической документации

Комплект программной документации на ПО **«Лабораторная информационно-управляющая система „Химические источники тока"»** (далее — **ЛИМС-ХИТ**; техническое обозначение в исходном коде — **BADB**, от англ. *Battery Assembly Database*, историческое) по ГОСТ 19 ЕСПД.

**Правообладатель:** ООО «РЭНЕРА» (ГК «Росатом»). Подразделение-разработчик — Центр химических источников тока.

**Область применения:** R&D химических источников тока (ХИТ) — электродные материалы, электролиты, сепараторы, ячейки и батарейные модули различных электрохимических систем.

**Класс ПО:** LIMS (Laboratory Information Management System).

**Текущий статус:** черновик версии 0.1.13, актуализирован 15 мая 2026 г. (первичная сборка — 22 апреля 2026 г.).

## Статус комплекта

- Всего документов: **8** (1 ведомость + 1 служебная карта + 6 основных документов ГОСТ 19).
- Общий объём: **~215 страниц** в печатной форме.
- Статус каждого документа: **черновик v0.1.13** (требуется ревью Мараулайте Д.К. и согласование с ООО «РЭНЕРА»).
- Комплект актуализирован под фактическое состояние `BADB_main/` на 15.05.2026: vanilla v1 является текущей release-candidate поверхностью для рабочих и справочных страниц; Vue рассматривается отдельно как задача синхронизации фронтенда с vanilla v1.
- В комплект включены текущие vanilla-страницы, печатные отчёты, фильтры списков, record-open/sticky-header паттерн, delete-check / typed-confirmation / dependency-conflict правила, `d031`/`d032` и методика миграционных проверок.
- Готовность к опытной эксплуатации: **release candidate для внутреннего лабораторного пилота**, но перед пилотным использованием ещё требуются прямое подтверждение `public.schema_migrations` на Windows/lab БД, проверка `d031` и ручная проверка destructive battery flow согласно `docs/current/release_readiness.md`.

## Известные ограничения текущей версии (заметки для ревью)

Пункты ниже — реально существующие ограничения реализации, которые нужно либо устранить, либо явно зафиксировать в документации:

1. **Content Security Policy отключена** в `app.js` (`helmet({ contentSecurityPolicy: false })`). Все остальные основные security headers от `helmet` включены; включение CSP требует отдельной политики nonce/hash и остаётся задачей будущего hardening.
2. **Нет автоматизированного runner-а миграций БД.** Миграции применяются вручную в порядке имён; авторитетный ledger применённых миграций — `public.schema_migrations`, созданный и backfill-нутый миграцией `d032_create_schema_migrations_table.sql`. Файлы `migrations_log.txt` остаются human checkpoint notes only.
3. **Нет скрипта автоматического создания пользователей.** Создание — только через SQL INSERT с предварительно захешированным паролем.
4. **Подсистема «Модули»** — vanilla-страница-заглушка `/workflow/4-modules.html`; не описывается как реализованный рабочий процесс текущей версии.
5. **Disk-backed uploads** (`uploads/electrochem`, `uploads/cycling`) пока раздаются Express статически через `/uploads`; переход на закрытые download-routes относится к future-плану.
6. **Vue parity** — отдельная задача синхронизации фронтенда с vanilla v1. Нельзя использовать текущее Vue-поведение как источник текущего vanilla-релиза там, где есть расхождение.

## Регламент изменений документации

### Принципы

- Документация является **живым** комплектом: отражает фактическое состояние ПО на каждый момент времени.
- При изменении кода, влияющем на требования, архитектуру, пользовательский интерфейс или процедуры эксплуатации, соответствующий документ (или несколько) **должен быть обновлён** в том же рабочем цикле, что и изменение кода.
- Все изменения документации отражаются в журнале (раздел ниже) с указанием даты, автора и краткого описания.

### Работы на неделе 22–27 апреля 2026 г.

Допустимы любые изменения в коде `BADB_main/`. При этом:

- При изменении функциональности — обновить соответствующие разделы документов 01 (ТЗ, §4.1) и 02 (Описание программы, §3).
- При изменении UI — обновить документ 04 (Руководство оператора).
- При изменении процедур установки/эксплуатации — обновить документ 05.
- При изменении структуры БД — обновить документ 03 (§3.4) и при необходимости 02 (Прил.В).
- При изменении API-контрактов — обновить `contracts/schemas/` и документ 02 (§3.2.4).
