# Аннотация

Настоящее техническое задание определяет требования к разработке программного обеспечения **лабораторной информационно-управляющей системы «Химические источники тока»** (далее — **ЛИМС-ХИТ** или **Система**; техническое обозначение в исходном коде — **BADB**), предназначенного для автоматизации учёта, обработки и научного анализа лабораторных данных полного цикла исследования и разработки **химических источников тока (ХИТ)**: электродных материалов, электролитов, сепараторов, собранных ячеек и батарейных модулей — от подготовки электродной ленты до электрохимических испытаний готовых изделий.

ПО разрабатывается как внутренний научно-исследовательский инструмент Центра химических источников тока ООО «РЭНЕРА» (ГК «Росатом»).

# 3. Назначение разработки

## 3.1. Область применения

Программа предназначена для применения в научно-исследовательских подразделениях Центра химических источников тока ООО «РЭНЕРА» для ведения R&D-разработок химических источников тока различных электрохимических систем: электродных материалов, электролитов, сепараторов, конструкций ячеек и батарейных модулей. Программа охватывает следующие технологические процессы:

1. Подготовка электродной ленты (подготовка активных материалов, взвешивание, смешивание, нанесение покрытия, сушка, каландрирование).
2. Нарезка электродов из готовой ленты (формирование партий нарезки).
3. Сборка батарей (монтаж стека электродов, заполнение электролитом, герметизация корпуса).
4. Контроль качества (QC) собранных батарей.
5. Электрохимические испытания — циклирование, снятие характеристик.
6. Научный анализ: расчёт ёмкости электродов и батарей, сравнение серий экспериментов, оценка уровня брака, прослеживаемость партий материалов.

## 3.2. Основные цели разработки

- **Централизация данных.** Замена разрозненных файлов Excel и локальных таблиц единым источником данных — реляционной СУБД.
- **Прослеживаемость (traceability).** Обеспечение сквозной связи между партией поставки материала, рецептурой ленты, параметрами нанесения покрытия, конкретным электродом, собранной батареей и результатами её испытаний.
- **Унификация терминологии и схемы данных** между четырьмя структурными подразделениями Дирекции по науке и образованию ООО «РЭНЕРА» (по миграции `018_department_real_names_and_assignments.sql`):
  1. Отдел исследований и разработок ХИТ;
  2. Отдел исследований и испытаний;
  3. Группа разработки новых материалов;
  4. Научно-образовательная группа.
- **Автоматизация научных расчётов.** Ёмкость электрода, поверхностная ёмкость, N/P-отношение, лимитирующая ёмкость батареи — on-demand вычисления по единой методике.
- **Аудит и контроль изменений.** Фиксация всех редактирований данных с возможностью восстановления истории.
- **Снижение трудозатрат.** Автозаполнение справочных полей, валидация входных данных, единые формы для всех лабораторий.

### 4.1.2. Подсистема управления справочниками

Назначение: ведение справочников материалов, рецептур, электролитов, сепараторов, пользователей, отделов, проектов.

#### 4.1.2.1. Справочник материалов

**Центральный справочник системы.** Реализует концепцию абстрактного материала и его рабочих экземпляров (**material instances**), поддерживающую рекурсивные смеси.

Структура (миграции `d026_add_material_sources_and_properties.sql`, `d027_add_material_source_and_property_files.sql`; первоисточники — `materials-inventory-context.md` Д.К. Мараулайте):

| Сущность | Назначение |
|---|---|
| `materials` | Абстрактное химическое определение материала (катод, анод, связующее, электролит и т.д.) |
| `material_instances` | Конкретные рабочие экземпляры: чистые закупленные партии, растворы, дисперсии, смеси |
| `material_instance_components` | Рекурсивное описание смесей: один экземпляр может быть составлен из других с заданными массовыми долями |
| `material_sources` | Информация о партии поставки: поставщик, бренд, каталожный номер, номер лота, даты заказа/получения, оценка качества |
| `material_properties` | Научные свойства материала: удельная ёмкость (`specific_capacity_mAh_g`), плотность (`density_g_ml`) |
| Файловые вложения | Сертификаты, паспорта качества, фотографии упаковки (хранятся в `uploads/`) |

Функции:

| № | Функция | Правило |
|---|---|---|
| 4.1.2.1.1 | Создание абстрактного материала | При создании автоматически создаётся один рабочий экземпляр «100% чистый» и связанная запись `material_sources` |
| 4.1.2.1.2 | Создание дополнительных экземпляров | Возможно создание дополнительных чистых экземпляров (с новой партией поставки) и производных экземпляров (смесей, растворов) |
| 4.1.2.1.3 | Оценка качества партии поставки | Метка (`quality_rating_label`): `good` / `ok` / `bad` / `tbd` (по умолчанию). Числовая оценка (`quality_rating_score`, 1–5, опционально). Текстовые заметки. |
| 4.1.2.1.4 | Отображение оценки в списке | На основной странице `Материалы` у экземпляров, привязанных к партии, отображается индикатор цветом: зелёный / синий (или серый) / красный / пусто |
| 4.1.2.1.5 | Связь экземпляра с партией | Поле `material_instances.source_id`; обязательно для чистых закупленных экземпляров, NULL для производных |
| 4.1.2.1.6 | Редактирование свойств | Отдельная страница `material-details`, доступная из любого экземпляра |
| 4.1.2.1.7 | Редактирование данных партии | Отдельная страница `material-source-info`, доступная только для чистых закупленных экземпляров |
| 4.1.2.1.8 | Прикрепление файлов к экземпляру | PDF, изображения, ограничение 6 МБ на файл (`uploads/`) |

#### 4.1.2.2. Справочник рецептур (tape recipes)

Рецептура ленты — именованный набор строк, определяющий состав смеси для нанесения покрытия. На уровне рецептуры задаётся роль (`role` = `cathode` / `anode`), определяющая, является ли рецепт катодным или анодным. Это позволяет при создании ленты выбирать только подходящие рецептуры.

Строки рецептуры (`tape_recipe_lines`) описывают компоненты:

- Активный материал (катодный или анодный), роль строки `cathode_active` / `anode_active`;
- Связующее (`binder`);
- Электропроводящие добавки (`additive`);
- Растворитель (`solvent`).

Для каждой строки задаются: массовая доля в сухом остатке в процентах (`slurry_percent`, 0..100), флаг «участвует в процентном расчёте» (`include_in_pct`), **абстрактный материал** (`material_id`). Конкретный экземпляр материала (`material_instance_id`) выбирается **при заполнении фактических значений** на этапе подготовки ленты, а не в рецептуре.

Функции:

| № | Функция |
|---|---|
| 4.1.2.2.1 | Создание, редактирование, удаление рецептур |
| 4.1.2.2.2 | Проверка суммы долей (≈ 100 % в рамках `include_in_pct = true`) |
| 4.1.2.2.3 | Связь рецептуры с конкретной лентой через внешний ключ |

### 4.1.3. Подсистема технологического процесса

Ядро системы. Реализует сквозной рабочий процесс: **лента → электроды → батарея → испытания**.

#### 4.1.3.1. Ленты (tapes) — восьмистадийный процесс

Лента — полуфабрикат, представляющий собой фольгу-токосъёмник с нанесённым активным покрытием. Процесс её изготовления состоит из восьми последовательных стадий:

| № | Стадия (пользовательская) | Код `operation_types.code` | Подтаблица параметров | Содержание |
|---|---|---|---|---|
| 1 | Подготовка активных материалов | `recipe_materials` | — (через `tape_recipe_line_actuals`) | Фиксация рецептуры и конкретных экземпляров материалов |
| 2 | Сушка активного материала | `drying_am` | `tape_step_drying` | Параметры: температура, атмосфера, длительность |
| 3 | Взвешивание | `weighing` | — (через `tape_recipe_line_actuals`) | Фактические массы компонентов |
| 4 | Смешивание | `mixing` | `tape_step_mixing` | Параметры сухого и мокрого смешивания: скорости, времена, вязкость, объём суспензии |
| 5 | Нанесение покрытия | `coating` | `tape_step_coating` | Параметры: зазор, скорость, метод нанесения; **тип нанесения** (см. 4.1.3.1.1) |
| 6 | Сушка ленты | `drying_tape` | `tape_step_drying` | Параметры сушки после нанесения |
| 7 | Каландрирование | `calendering` | `tape_step_calendering` | Параметры уплотнения |
| 8 | Сушка каландрированной ленты | `drying_pressed_tape` | `tape_step_drying` | Финальная сушка |

На уровне СУБД все стадии проходят через общую таблицу `tape_process_steps`, связанную с `tapes`; тип стадии идентифицируется по `operation_type_id` (FK на справочник `operation_types`). Подтаблица `tape_step_drying` используется для трёх сушильных стадий (АМ, ленты, прессованной ленты); различие стадий — через `operation_type_id` родительской строки.

**4.1.3.1.1. Тип нанесения (coating sidedness).**

Обязательный параметр стадии 5. Принимает значения `one_sided` (одностороннее) или `two_sided` (двустороннее). Хранится в `tape_step_coating.coating_sidedness` (миграция `d024`).

Это свойство **не выбирается** на уровне электрода или батареи, а **наследуется** от источника:

```
Лента (источник истины) → Электрод (только чтение) → Батарея (проверяется на согласованность)
```

Правила (первоисточник — `Sidedness.md` Д.К. Мараулайте):

- На уровне электрода `sidedness` отображается, но **не редактируется**.
- В одной батарее запрещено смешивание электродов с разным типом нанесения. При попытке добавить несоответствующий электрод — операция блокируется с сообщением: `Нельзя смешивать 1- и 2-сторонние электроды в одной ячейке`.
- В выпадающих списках выбора ленты / партии электродов тип нанесения отображается как часть подписи: `Лента A (одностороннее)`.

**4.1.3.1.2. Фактические значения рецептуры (recipe actuals).**

Для каждой строки рецепта оператор вводит фактическое значение. Таблица `tape_recipe_line_actuals` (поля `measure_mode` — `mass` | `volume`, `actual_mass_g`, `actual_volume_ml`). Ровно один из двух режимов должен быть задан на строку (или строка пустая).

**4.1.3.1.3. Конвертация масса ↔ объём через плотность.**

Если материал имеет заполненное свойство `density_g_ml`, система автоматически отображает производное значение:

```
При вводе массы   → показывается эквивалентный объём
При вводе объёма  → показывается эквивалентная масса
```

Производное значение отображается меньшим шрифтом под введённым значением. Канонический (вводимый оператором) режим сохраняется как источник истины; производное значение не перезаписывает введённое.

При отсутствии плотности — показывается предупреждение: `Плотность не указана: масса не может быть рассчитана автоматически.`

#### 4.1.3.2. Электроды (electrodes) — нарезка партиями

Электрод — физический объект, нарезанный из ленты по заданной геометрии.

Концепция «партии нарезки» (`electrode_cut_batches`): одна операция нарезки производит множество однотипных электродов. На уровне партии хранятся: источник (`tape_id`), геометрия (`shape` = `circle` или `rectangle` + `diameter_mm` или `length_mm`/`width_mm`), целевой форм-фактор (`target_form_factor`, `target_config_code`), комментарии. Измерения массы фольги и параметры сушки хранятся в связанных таблицах `foil_mass_measurements` и `electrode_drying`. Фактическое количество электродов определяется числом строк в `electrodes` с соответствующим `cut_batch_id`.

Поддерживаемые формы: круг (диаметр), прямоугольник (ширина × высота), формат pouch (с параметрами корпуса).

**4.1.3.2.1. Измерения массы фольги (foil mass measurements).**

Обязательная характеристика партии. Позволяет определить массу покрытия каждого электрода:

```
масса покрытия = масса электрода − средняя масса фольги по партии
```

Несколько измерений на партию, вычисляется среднее.

**4.1.3.2.2. Поля электрода.**

Индивидуальные записи `electrodes`: масса (`electrode_mass_g`), статус (`status_code`: `1` — на складе / `2` — использован в батарее / `3` — забракован), причина брака (`scrapped_reason`, если применимо), номер в партии (`number_in_batch`), ссылка на использовавшую батарею (`used_in_battery_id`, при статусе `2`).

**4.1.3.2.3. Расчёт ёмкости (on-demand).**

Расчёты производятся серверной частью по запросу (не сохраняются в БД в версии 1.0 — источник `capacity-calculations-context.md` и `capacity-calculations-implementation-plan.md`):

Для каждого валидного (не бракованного) электрода:

```
масса покрытия (г)     = масса электрода − средняя масса фольги
масса активного (г)    = масса покрытия × доля активного
ёмкость (мА·ч)         = масса активного × удельная ёмкость материала
```

Система вычисляет ёмкость в двух параллельных режимах:

| Режим | Источник доли активного материала |
|---|---|
| Теоретический (theoretical) | `tape_recipe_lines.slurry_percent` |
| Фактический (actual-derived) | Из сохранённых `tape_recipe_line_actuals`, знаменатель — сумма масс сухих компонентов (растворитель не учитывается) |

Средние значения по партии рассчитываются **только по не бракованным** электродам. Забракованные электроды показывают свою ёмкость индивидуально, но в среднее не включаются.

На уровне партии также рассчитываются:

- Поверхностная ёмкость: `мА·ч/см²` = средняя ёмкость / площадь электрода.
- Ёмкость на сторону: поверхностная ёмкость / количество сторон (1 для одностороннего нанесения, 2 для двустороннего).

При отсутствии любого из входов (нет измерений фольги, нет плотности, нет удельной ёмкости) соответствующее производное значение возвращает `NULL`; в интерфейсе отображается прочерк «—».

#### 4.1.3.3. Батареи (batteries) — сборка, контроль качества, электрохимия

Батарея — готовый электрохимический элемент, собранный из электродов, сепаратора и электролита.

**4.1.3.3.1. Форм-факторы.**

Поле `batteries.form_factor` принимает одно из трёх значений (CHECK-ограничение в схеме): `coin` / `pouch` / `cylindrical`.

Для форм-фактора `coin` в подтаблице `battery_coin_config` различаются **две подкатегории** через поле `coin_cell_mode`: `half` (полуячейка с литиевой фольгой в качестве противоэлектрода) и `full` (полная монета с двумя рабочими электродами). Таким образом на уровне пользовательской логики различаются **четыре конфигурации:**

| Конфигурация (логическая) | form_factor | coin_cell_mode | Особенности |
|---|---|---|---|
| Монета половинная (полуячейка) | `coin` | `half` | Один рабочий электрод, противоэлектрод — литиевая фольга |
| Монета полная | `coin` | `full` | Один катод + один анод |
| Pouch (мягкая ячейка) | `pouch` | — | Возможен многослойный стек; параметр `pouch_case_size` |
| Цилиндрический элемент | `cylindrical` | — | Многослойная намотка; подтаблица `battery_cyl_config` |

Ограничения выбора электродов (первоисточник — `electrodes-logic.md` Д.К. Мараулайте):

| Конфигурация | Источники электродов (tapes × batches) | Электроды в стеке |
|---|---|---|
| Монета половинная (`coin`+`half`) | Ровно один: катодная лента или анодная лента | Один электрод (`1C` или `1A`) |
| Монета полная (`coin`+`full`) | Ровно один катодный и один анодный источник | Один катод + один анод |
| Pouch, цилиндрическая | Ровно один катодный и один анодный источник | `катоды = аноды` или отличие на 1 |

**4.1.3.3.2. Стадии жизненного цикла батареи.**

| № | Стадия | Содержание |
|---|---|---|
| 1 | Сборка | Выбор электродов, сепаратора, электролита; фиксация параметров сборки (давление, dry-box state) |
| 2 | Контроль качества (QC) | Параметры внешнего контроля: вес, размеры, осмотр |
| 3 | Электрохимические испытания (первичные) | Загрузка файлов электрохимии (PDF-отчётов), до 6 МБ на файл |

**4.1.3.3.3. Расчёт ёмкости батареи (on-demand).**

По набору выбранных электродов:

```
Σ катодов  = сумма ёмкостей выбранных катодных электродов
Σ анодов   = сумма ёмкостей выбранных анодных электродов

Лимитирующая ёмкость = min(Σ катодов, Σ анодов)
N/P                  = Σ анодов / Σ катодов
```

Обе пары значений — теоретические и фактические — рассчитываются параллельно.

Для полуячеек (`form_factor='coin'` + `coin_cell_mode='half'`) отображается только ёмкость рабочего электрода; лимитирующая ёмкость и N/P не применяются.

Бракованные электроды исключаются из расчёта.

### 4.1.4. Подсистема электрохимических испытаний (циклирование)

- Энергия заряда / разряда (мВт·ч);

**4.1.4.4. Стилевые пресеты графиков.**

### 4.1.5. Подсистема аудита и контроля изменений

Трёхуровневая система аудита:

**4.1.5.1. Журнал аутентификации (`auth_log`).**

Append-only. Записи: успешный вход, неуспешная попытка, регистрация, выход. Поля: пользователь, IP-адрес, User-Agent, результат, временная метка. Интерфейс просмотра — `AuditPage.vue`.

**4.1.5.2. Журнал активности (`activity_log`, миграция 012).**

Агрегация CRUD-операций и событий аутентификации. Поля: тип действия (create / update / delete / auth), пользователь, сущность (таблица и идентификатор), временная метка. Интерфейс — `ActivityPage.vue`.

**4.1.5.3. Журнал изменений полей (`field_changelog`, миграция 013).**

Самый детальный уровень. Для каждой операции `UPDATE` записываются **все изменившиеся поля** с их значениями «до» и «после». Триггеры вызываются автоматически middleware-слоем `trackChanges.js`. Интерфейс просмотра — `FieldChangelog.vue`.

**4.1.5.4. Ограничения целостности.**

| Таблица | Разрешённые операции |
|---|---|
| `raw_submissions` | Только `INSERT` |
| `auth_log` | Только `INSERT` |
| `field_changelog` | Только `INSERT` |

Удаление и обновление записей в этих таблицах запрещено на уровне бизнес-логики.

**4.1.5.5. Оптимистичная блокировка.**

В таблицах `tapes`, `electrodes`, `batteries`, `tape_recipes`, `projects` присутствует поле `version` (миграция 003), увеличиваемое на 1 при каждом `UPDATE`. При обновлении клиент передаёт ожидаемое значение; сервер проверяет условие `WHERE version = $expected` и при несовпадении возвращает HTTP 409 Conflict. Таблицы-справочники (drying_atmospheres, coating_methods и др.) и append-only журналы поле `version` не содержат.

### 4.1.6. Подсистема приёма данных (submissions)

Назначение: приём данных из внешних источников (в первую очередь — из Excel-клиента; возможна интеграция с другими системами).

Таблица `raw_submissions` (миграция 002): append-only хранилище всех поступивших данных с указанием источника (`source`: `excel` / `api` / `import`) и временной метки. После валидации и трансформации данные попадают в нормализованные таблицы (tapes, electrodes, …).

Валидация производится по JSON-схемам из `contracts/schemas/`:

- `tape_prepare.v1.json` — подготовка ленты;
- `electrode_cut.v1.json` — нарезка электродов;
- `battery_assembly.v1.json` — сборка батареи.

Схемы версионированы. При необходимости изменения структуры контракта создаётся новая версия (например, `v2.json`); существующие версии никогда не редактируются.

## 4.2. Требования к надёжности

**4.2.1.** Сохранность данных:

- Append-only журналы (`auth_log`, `raw_submissions`, `field_changelog`) — отсутствие возможности удаления исторических данных.
- Автоматические бэкапы СУБД средствами `pg_dump` — см. раздел 4.5.5.
- Миграции схемы — строго forward-only: ранее применённые миграции не редактируются.

**4.2.2.** Обработка отказов:

- При потере соединения с СУБД — HTTP 500, клиент отображает сообщение: `Сервер недоступен, повторите попытку позднее`.
- При конфликте оптимистичной блокировки — HTTP 409, клиент предлагает перезагрузить данные.
- При невалидном JSON-теле запроса — HTTP 400 с описанием нарушения схемы.

**4.2.3.** Контроль целостности данных:

- Валидация всех входных данных по JSON-схемам.
- Ограничения внешних ключей (`FOREIGN KEY`) на уровне СУБД.
- Уникальные ключи на идентификаторах партий, номерах лотов и т.п.

**4.2.4.** Отказоустойчивость клиента:

- При потере токена — автоматическое перенаправление на страницу входа с сохранением исходного маршрута.
- Кэширование справочных данных (`useBackendCache.js`) с политикой stale-while-revalidate.

## 4.3. Условия эксплуатации

**4.3.1. Среда эксплуатации:** локальная сеть (LAN) внутри периметра ГК «Росатом». Отсутствие доступа в публичный Интернет — ни со стороны сервера, ни со стороны клиента, в контексте работы Системы. Отсутствие внешних API-зависимостей.

**4.3.2. Доступ:** через корпоративную сеть по TCP/IP. Адресация — IPv4. При необходимости — ограничение пула IP-адресов через `ALLOWED_IPS`.

**4.3.3. Режим работы:** непрерывный, круглосуточный, 7 дней в неделю. Плановые остановки — для обновления и резервного копирования.

**4.3.4. Квалификация пользователей:** лабораторный персонал, имеющий базовые навыки работы с ПК и веб-интерфейсами. Специальная IT-подготовка не требуется.

**4.3.5. Квалификация администратора:** системный администратор с навыками работы с Windows (установка ПО, управление службами, Task Scheduler, PowerShell), а также PostgreSQL и Node.js; при альтернативном развёртывании на Linux — соответствующие навыки Linux.

**4.3.6. Схема развёртывания (текущая):** серверная часть функционирует на выделенном Windows-компьютере в локальной сети подразделения. Рабочие места сотрудников подключаются к серверу через маршрутизатор (проводное и/или Wi-Fi-подключение в зоне покрытия). Сервер не имеет выделенного доменного имени и выхода в публичный Интернет.

## 4.8. Специальные требования

### 4.8.1. Требования к безопасности информации

**4.8.1.1. Ограничение сетевого периметра.**

- Система функционирует **только в локальной сети** корпоративного периметра ГК «Росатом».
- В коде и конфигурации отсутствуют обращения к внешним API, сервисам, CDN, платформам аналитики.
- Клиентские статические ресурсы (шрифты, библиотеки) упаковываются в сборку; загрузка из внешних источников исключена.

**4.8.1.2. Хранение учётных данных.**

- Пароли пользователей — в виде хешей (bcrypt, не менее 10 раундов).
- Хеш соли — встроен в bcrypt-хеш, отдельное хранение не требуется.
- Токены — не хранятся на сервере после генерации; проверка валидности — по криптографической подписи с использованием `JWT_SECRET`.
- `JWT_SECRET` — обязательная переменная окружения в продуктивном режиме; при запуске без неё сервер завершает работу с ошибкой.

**4.8.1.3. Защита от атак.**

| Угроза | Средство защиты |
|---|---|
| Перебор паролей (brute-force) | 10 неуспешных попыток → блокировка на 1 ч |
| Гонка условий при переборе | `pg_advisory_xact_lock` на логин при неудачной попытке |
| DDoS | Rate limiting 300 запросов/мин на IP |
| XSS | Экранирование пользовательского ввода средствами Vue (`{{ }}` интерполяция, автоматический escape HTML); HTTP-заголовки безопасности через `helmet` (X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Cross-Origin-*). **Content Security Policy временно отключена** в `app.js` на время миграции на PrimeVue (inline-стили PrimeVue требуют отдельной политики nonce/hash); возобновление — в ближайшей итерации |
| CSRF | Bearer-токен (не cookie); защита не через `SameSite`, а через проверку заголовка |
| SQL-инъекции | Параметризованные запросы `pg` (без конкатенации строк) |
| Несанкционированный доступ | Ролевая модель, проверка принадлежности ресурса пользователю / проекту |
| Утечка токена | Короткий срок действия (8 ч), инвалидация при смене пароля |
| Несанкционированный IP | Опциональный `ALLOWED_IPS` на CIDR-диапазон |

**4.8.1.4. Ведение журнала безопасности.**

Все события аутентификации, изменения прав, операции с ролевой моделью — в `auth_log` и `activity_log`. Журналы защищены от модификации и удаления.

**4.8.1.5. Инварианты безопасности на уровне сборки.**

При запуске в production (`NODE_ENV=production`) выполняются обязательные проверки:

- `JWT_SECRET` задан и не равен значению по умолчанию.
- `AUTH_BYPASS` отсутствует или равен `false`.
- Используется соединение HTTPS (в зоне прокси / reverse proxy).

### 4.8.2. Требования к производительности

*(@уточнить: требуемые показатели. Ниже — ориентировочные на основе текущего поведения.)*

## 8.2. Виды испытаний

- **Внутренние испытания** — силами разработчиков до передачи на опытную эксплуатацию.
- **Опытная эксплуатация** — в условиях лаборатории на реальных данных в течение согласованного периода (@уточнить длительность — рекомендуется не менее 30 календарных дней).
- **Приёмо-сдаточные испытания** — по завершении опытной эксплуатации, с оформлением:
  - Акта изготовления (п. 5.7);
