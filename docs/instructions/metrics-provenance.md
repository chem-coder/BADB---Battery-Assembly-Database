# Происхождение метрик (provenance) — контракт и правила

Статус: фаза 1 реализована на /cycling (2026-06-10). Автор: Dima.
Цель: для любого вычисляемого значения пользователь видит **откуда оно** —
формулу, подставленные числа, цепочку данных, источник — и может **перепроверить
расчёт одной кнопкой**. Без галлюцинаций: по построению, а не по дисциплине.

## Архитектура

```
contracts/metrics.v1.json          ← ЕДИНЫЙ источник: формулы, входы, lineage,
                                     где вычисляется, шаблоны объяснений
contracts/metrics-golden.v1.json   ← golden-векторы (вход → эталонный выход,
                                     посчитаны вручную)
        │
        ├── client-web/__tests__/utils/metricsConformance.test.js   (vitest)
        ├── scripts/cycling-file-import/test_metrics_conformance.py (python3,
        │     гоняет ТЕ ЖЕ векторы через scripts/parse_cycling.py И
        │     import_cycler_file.py)
        └── client-web/src/utils/metricsEngine.js  ← клиентский слой:
              getMetric / computeMetric / computeStreamSummary /
              explainMetric (подстановка, без eval) / verifyMetric
        │
client-web/src/components/ProvenancePopover.vue  ← одна компонента на систему
```

## Принципы (нарушение = баг)

1. **Объяснение = тот же код, что и расчёт.** Текст формулы — только из
   контракта; числа — подстановкой в `explain_template`; никакой генерации
   текста и рукописных дублей в компонентах.
2. **Перекрёстный конформанс.** Любая реализация метрики (сервер, Python,
   клиент) обязана проходить общие golden-векторы. Меняешь формулу → меняешь
   контракт (v2!) и векторы → CI заставит выровнять ВСЕ реализации.
3. **Сверка, а не доверие.** Для хранимых величин поповер умеет «Перепроверить»:
   живой пересчёт канонической агрегацией (`computeStreamSummary`, зеркало
   `parse_cycling.py`) против значения в БД, с допуском на округление при
   записи (CE/EE — 2 знака, V — 4).
4. **Пусто лучше выдумки.** Поповер рендерит только то, что реально есть в
   контракте/БД. Нет данных — «происхождение не зарегистрировано», не догадка.
5. **Терминология аудита.** Время — через MSK-утилиты, разделение business/audit
   (`item_created_at` vs `created_at`). Подпись «записано в систему», НЕ
   «выполнил» — оператор появится после колонок `operator_user_id`/`performed_at`
   (см. docs/instructions/operator-vs-creator.md).

## Найдено и исправлено при внедрении (фаза 1)

- **Расхождение конвенций в одной колонке БД**: `parse_cycling.py` пишет
  `avg_*_voltage_v` как простое среднее по точкам (публикационная конвенция),
  а navani-импортёр писал ёмкостно-взвешенное ⟨V⟩=∫V·dQ/Q. Импортёр выровнен
  на канон (2026-06-10); конвенция зафиксирована в контракте.
- **σ в протокольном сравнении** — выборочное (n−1), не популяционное:
  контракт зафиксировал реальность реализации (поймано конформанс-тестом).
- **Рукописная панель формул успела задрейфовать** (описывала скользящее
  среднее как дефолт dQ/dV после перехода на Сав-Гол) — переведена на контракт.

## Как добавить метрику

1. Запись в `contracts/metrics.v1.json` (если меняешь существующую формулу —
   это `metrics.v2.json`, v1 не редактируется после мерджа).
2. Golden-векторы в `metrics-golden.v1.json` (посчитанные вручную).
3. Реализации + прогон обоих конформансов:
   `cd client-web && npx vitest run __tests__/utils/metricsConformance.test.js`
   `python3 scripts/cycling-file-import/test_metrics_conformance.py`
4. UI: `provRef.open(event, { metricId, value, inputs, points?, storedKey?, source })`.
