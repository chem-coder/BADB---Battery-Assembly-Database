## Язык

- **Проза — русский.** Заголовки разделов, описания, комментарии, таблицы — всё на русском.
- **Технические идентификаторы — английский** (имена таблиц БД, полей, переменных окружения, маршрутов API). Это норма для технической литературы.
- **Команды и код — дословно** в код-блоках, без пересказа прозой.
- **Стиль — сухой, точный, без эмоций.** Целевой читатель — Чудинов Е.А. (заказчик) и приёмная комиссия Росатома; не клиент в маркетинговом смысле.

## Запрещённые упоминания (feedback_no_external_mentions)

В техдоке **нельзя** упоминать конкретные внешние сервисы:

- ❌ GitHub (как сервис) — заменить на «корпоративный git-репозиторий», «система управления версиями».
- ❌ Claude / Claude Code / Anthropic / Sonnet / Opus — заменить на нейтральное «инструменты разработчика», либо вообще не упоминать.
- ❌ ChatGPT / GPT / OpenAI — то же.
- ❌ Cursor / Copilot / любые другие AI-IDE.
- ❌ Внешние SaaS-сервисы хостинга, аналитики, мониторинга.

**Можно**:
- ✅ Git как технология контроля версий (open-source, общепринятая).
- ✅ Названия open-source библиотек из `package.json` (helmet, express, vue, etc.) — это часть стека.
- ✅ PostgreSQL, Node.js, Python — стандартные платформы.

Если в комментарии или примере встречается имя файла из набора Claude Code (`CLAUDE.md`, `.claude/`) — используйте нейтральную формулировку: «файл правил разработки репозитория», «правила репозитория».

## Версионирование

- Версия комплекта — в `README.md` (frontmatter `status:` и блок «Текущий статус»).
- Версия отдельного документа — в его собственном frontmatter (`version:`).
- При содержательной правке любого документа — bump патч-версии комплекта (0.1.7 → 0.1.8) **и** запись в журнале ревизий в `README.md`.
- При правке только нескольких документов — в README прямо указать «содержательно правлен только документ N; остальные не менялись с предыдущей ревизии».

## Журнал ревизий (формат записи)

```markdown
| YYYY-MM-DD | 0.1.X | Меняйлов Д.С. | **<Краткое название>.** <Подробное описание правок с номерами разделов: §X.Y.Z — ...; §A.B — ... Перечислять конкретные изменения с привязкой к разделам, не общие фразы.> |
```

Пример из v0.1.7:
> Документ 03 (Пояснительная записка): обновлены ERD трёх доменов с учётом миграций d028–d030 (связи «многие ко многим» с проектами): §3.4.6 — `tape_projects`, §3.4.7 — `electrode_cut_batch_projects`, §3.4.8 — `battery_projects`. Поля `*.project_id` в основных таблицах сохранены как «исходный» проект; общая статистика БД (§3.5.1) — таблиц ≈ 58 → ≈ 61.

## Маркер `@уточнить`

Используется для открытых вопросов, требующих ответа от заказчика / руководителя. Перед формальной передачей комплекта — все `@уточнить` должны быть либо закрыты, либо явно перенесены в раздел «Открытые вопросы» в README.

## Перекрёстные ссылки

Документы тесно связаны. При правке одного — проверить, не нужно ли синхронизировать:

- Doc 01 (ТЗ) §4.5.1 «Программные платформы» ↔ `package.json` версии библиотек.
- Doc 01 (ТЗ) §4.8.1 «Безопасность» ↔ Doc 05 §3.2 (реализация helmet/rate-limit/lockout) ↔ Doc 06 ТК-AUTH-* (тест-кейсы).
- Doc 02 (Описание) §3.2.6 «Миграции» ↔ файлы в `migrations/` (диапазон номеров).
- Doc 02 Прил. А «Маршруты API» ↔ `routes/*.js` (фактические эндпоинты).
- Doc 03 (Пояснительная) §3.4 «ERD» ↔ схема БД (миграции, добавляющие таблицы).
- Doc 06 (ПМИ) тест-кейсы ↔ Doc 01 (ТЗ) требования.

При несинхронности — фиксировать в журнале ревизий, какой документ обновлён и какие остались на следующую ревизию.

## После правки

1. Bump `version:` во frontmatter правленного документа.
2. Bump `status:` в `README.md` frontmatter.
3. Добавить запись в журнал ревизий README.
4. Обновить «Дата последней актуализации» в `00. Ведомость комплекта документации.md`.
5. Если правлен документ 01 (ТЗ) — обновить «Статус» в строке этого документа в Ведомости §1.1.
6. Если изменения содержательно затрагивают сквозные сущности (роль, флаг, эндпоинт, таблица) — обновить Карту инвентаризации (`00. Карта инвентаризации.md`) с кросс-ссылкой `(Doc XX §Y.Z)`.
